# PyTorch加速：连续定位、实施、复核，直到有据收口

遵循 `goal-first`：目标是缩短算法研究的实际等待。**沿“目标 → 分阶段基线／timeline → 选手段 → 真实验收 → 重判剩余关键路径”循环推进；首个提速不等于整轮完成。** 下发受限先试 graph／compile，设备受限先用现成接口／融合；按瓶颈选工具。

## 必须执行：新优化负责整轮闭环，不是只交首个提速

主动诊断、推进与收尾是 Agent 的责任：不等用户发现仍慢，再来追问“看过 timeline 没有／还有什么手段”。下面六步都要走到；已有证据可以复用，工具按瓶颈选择。

1. **先商榷边界**：确认实际任务、可接受等待、资源与预算，给出首个判断和路线。中途可以讨论；重大方案取舍，或语义、范围、资源、预算发生实质变化时再确认。授权范围内的常规下一步由 Agent 主动继续。
2. **先看全链**：用真实代表输入拆出各主要阶段，读取或补齐相关 host／runtime／device timeline。生成区分 prefill／decode，训练覆盖完整 step；一段提速后仍要检查其他主要阶段。
3. **按证据选动作**：说明当前主导成本、为何选这一层、预期改善及怎样验证。命中条件就执行有界对照；实施指实际跑出对照结果。
4. **验证候选**：在真实调用上核数值、覆盖、冷暖成本与端到端净收益。失败只否定该候选，其他阶段和同类工具仍按证据判断。
5. **每次实质改动后回看**：重测阶段耗时，分析仍适用的真实 timeline，关键路径变了就补采。重新回答“现在最慢在哪、下一项是什么、为何继续或停止”。
6. **有价值的下一步接着做**：目标未达、预算尚有且存在证据支持的可行候选，就继续定位 → 实施 → 验收。需要越界或已阻塞时，明确商榷或暂停；本轮只在第 6 节的出口结束。

“已有 kernel”“已经用 Graph”“已快两倍”“只承诺有界尝试”都不是停止依据。有界限制的是投入，闭环仍要走完；闭环也不要求固定轮数、满载、穷尽工具或重复已有的有效证据。

## 0. 目标、契约与预算

- 固定研究任务、可接受等待和本轮预算；按 `剩余运行次数 × 每次可省时间` 衡量开发、验证、冷启动和维护成本。停止以第 6 节出口为准；不设统一的利用率／功率／倍数门槛。
- 保留算法、dtype、样本和评分协议。先选 setting，再在同一方法比较组内统一 batch、后端、attention 和调度。跨 setting 的 logits／生成／逐题分数可以不同；实现数值、统计轴／padding、覆盖与评分必须有效。
- 设置变化另记，旧 setting 的基线不混用。改变定标定义、把伪量化换成真低位计算属于语义变化，按算法改动处理，不计作执行优化。
- 分工：本 skill 管 PyTorch 执行组织、接口、graph／compile 和模型接入；DSL、tile、片上流水与专业 kernel 迭代归 `kernel-knowledge`；推理引擎研发另立目标。
- 全量评测时间预测用 `eval-time-estimate`：本 skill 选定并验收加速路径后，由它安排代表性短测、跨批稳定性、冷暖成本及全量外推；估时任务里不重复调优。

**训练入口**：涉及 forward → backward → optimizer 时先读[训练分支](references/training.md)。先固定算法和梯度契约，核对算法接入后哪些高效路径仍在，再按数据／前向／反向／通信／更新的关键路径行动。训练数据多、功率或利用率高都不能代替 timeline；长 kernel 已覆盖下发时不强推 Graph。推理的关梯度／输出复用经验不直接搬到训练。

## 1. 全量前先加速，已验路径持续复用

**用户要求长训练、全量或批量评测时，主动先查加速证据。新路径完成实际尝试和真实调用验收后再启动长任务。** 正确性 smoke、profile 和建议清单都只是中间步骤。高效路径未受破坏且已有适用证据时直接复用，不必再跑 Graph 或工具矩阵。

| 当前情况 | 应做什么 |
|---|---|
| 首次执行，或没有适用的已验加速路径 | 代表性基线／timeline → 第 2–5 节实施 → 第 6 节验收并回看，循环到有据收口再全量；首个提速不等于整轮完成 |
| 已完成加速，执行路径和覆盖仍有效 | 核对实际入口／配置后直接复用；每次全量、换会话、重启、换题或扩大题量都不需要重复短测／profile／调优 |
| 主流程方法改变，或执行／shape 超出覆盖 | 沿同一方法只补受影响阶段的加速与验收，其余复用；完成后继续已授权的全量 |

- 变化按实际影响判断：模型结构、在线算子链、生成／cache 路径、后端／设备放置或未覆盖的 shape 可能使证据失效；仅数据值、种子、题量或不影响执行链的代码修改不重开。正常编译／暖机、缓存更新和必要的正确性检查照常保留。
- 训练另核反向／loss 归一化、optimizer／AMP、重计算与并行方式，变化只补相关证据。“数据量少”与“每步计算少”分开看；短训练先算冷构建能否回本。
- 在已有报告／任务记录里保存采用的入口／配置、执行与 shape 覆盖、实测前后耗时、冷成本和结论。**全量必须实际使用已验路径**：在别的脚本里试过候选、知道通用思路或持有旧似然成绩，都不证明当前生成路径已加速。
- 单个候选无净收益时，保留实测、回退，并重选当前关键路径。已验且满足当前任务的路径直接复用；不设必达倍数，不新增审批或管理文件。
- 需要新短测时，用真实代表输入分列加载、离线／冻结准备、冷编译／预热、在线评分；生成另拆 prefill／decode，记录实际 shape、步数及有效吞吐。复用时直接引用已有测量，按本批规模更新预计成本，并标明是外推。
- 先记 host 阶段 wall 和内存峰值；功率、忙碌度和 HBM 旁路采样作辅助，缺项写明，不为填满指标延长实验。累计 kernel Duration 不能当 wall。
- 沿热调用展开“数据准备 → 统计／参数 → 变换 → 库算子 → 输出／cache”，记录层／专家／步数带来的调用放大。一个 Python 函数或算法步骤可能下发几十个 kernel；最终核已经存在，整条链仍可能低效。
- 放行判据：当前路径的闭环与真实验收证据齐全，或适用的既有证据完整覆盖；已验 setting 满足整批预算后按授权启动全量。阶段暂停、用户停止、只有基线或只有首个提速，都不构成放行。

## 2. 先做便宜且确定的改进

按证据命中项处理，不逐行打卡；详细搜索与计时模板见 [checklist](references/checklist.md)。

| 先查什么 | 优先动作／保留条件 |
|---|---|
| 不需要的工作 | eval 关梯度，去掉无用的 hidden、attention 和全词表输出；纯似然不用 KV，生成保留；训练／校准所需的图不删 |
| 重复准备／常量 | 离线在线分开，缓存 tokenize／权重量化／静态规则与 mask；绑定版本、device、dtype；动态统计不能缓存 |
| 冗余驻留／临时量 | 按 storage 去重权重与 packed 副本，缩短引用寿命，安全复用 buffer；保留训练 master／恢复所需；reserved 单独看，不计入活内存 |
| 同步击穿流水 | 热循环里的取值、日志、标量上传、动态索引、重复 copy 移出或合批；后端内部同步以 trace 定因，保留正确依赖 |
| 无效 batch／padding | 少量 batch 对照、长度分桶和动态 padding，看有效 tokens/s 及峰值；保持独立定标组，容量上限实测得出 |
| 独立工作被串行化 | 向量化、batched／grouped、合并共享输入投影、预取；核对实际 dispatch（接口名带 fused 也要核对） |
| 阶段间可重叠 | 数据准备与计算、独立分支、跨设备的不同完整 batch；保持 Event／tensor 寿命；复杂流水线按证据另作有界候选 |
| 现成高效接口 | 核对目标设备的上游／Torch／厂商实现和 fallback，按算法契约短验；CUDA 文档的结论不直接套到其他平台 |

- `model.eval()` 与推理上下文按用途使用；会跨 inference／no_grad 原位更新的持久 buffer，须冷建为普通张量或约束上下文。
- Batch／layout 优化要计入 copy、cast、contiguous 和临时内存，不为占满设备增加无用输入。显式同步清理完后，仍可能有逐操作下发空窗。
- 本步出口：此类浪费已处理或确认没有对应问题，随后进入第 3 步重判剩余成本；**首个提速不等于整轮完成**。已有有效 timeline 直接复用，不为进入下一步重复采集。

## 3. 读timeline：把“空闲很多”变成可行动判断

**本轮新优化必须取得或复用代表性应用 timeline 并实际分析。** 主动看全窗和局部，不等用户要求画图；定位要落到具体阶段和成本；热点表、“75% 空闲”或“很多小 kernel”只是起点。采不到就写明具体阻塞，本步记为未完成。

**人类查看按用户触发**：用户说想看 timeline／导出 Perfetto 时，按[下载查看流程](references/timeline-viewing.md)用本包脚本生成兼容文件，交付下载链接并说明模型／算子、版本和采集范围。默认让用户下载后在 Perfetto 打开；不默认启动可视化服务，也不要求安装 kernel-knowledge。Agent 日常的自动分析照常进行。

- 同窗对齐 host 线程、runtime launch／graph replay／copy／sync，以及全部相关设备 stream；核对进程、物理卡、采集边界和缺失关系。生成分阶段读，另留未插桩的计时锚点。
- 先看全窗确定阶段，再放大代表性空窗：是长块等待，还是每两个短 kernel 之间的密集微间隔？核对首尾与窗内分布；需要展示时给真实 timeline 的总览加局部放大，不用示意图充当证据。
- 单卡看相关 stream 的并集，多卡另看共同无任务区间；“一张卡等另一张”与“所有卡一起空白”分开判断。设备无任务记录不自动等于 CPU 在计算，host API 时间也可能与设备工作重叠。

| 时间线与调用证据 | 下一有效动作 |
|---|---|
| 密集短 kernel＋持续微空窗，稳定高频 eager 链 | **主动做完整稳定片段的 graph 保计算对照**，或用已适配的 compile。计入输入 copy 与输出消费，先不抠单核 Duration |
| host 等同步／取值／复制，或数据供给断档 | 定位真实依赖、重复搬运／准备，回第 2 步；graph 消不掉必要依赖 |
| 一卡工作、另一卡等待 | 核对阶段调度；有独立 batch 才考虑流水线，`device_map` 只管放置，并行要另行调度 |
| 长 kernel／中间流量实占关键路径 | 先现成接口／compile 融合，再有界 kernel 外援 |
| 设备连续有工作但算力低 | 核对实际 shape、带宽、访存延迟与批量；低算力不直接等于 HBM 饱和 |
| host 关系缺失／因果仍不清 | 写明未知，用最小保计算对照区分；缺项不按零成本处理，追因也不阻塞低成本验证 |

- 判定下发主导，需要 host 关联或“保持计算、减少逐操作下发”的对照支持；按证据强度表述，共同空窗不能直接换算成可兑现的加速。
- 机制、区间口径、放大图与消融见 [execution-chain](references/execution-chain.md)；设备监控及平台工具入口见 [device-observation](references/device-observation.md)。
- 本步出口：明确阶段、主要成本、待证假设及一个有界动作，随后在授权预算内实施。诊断之后接着实施，已有的倍数也一样；残余空窗按预算处理。

## 4. 下发受限：graph是优先验证的执行方式

Graph 缓存设备工作及依赖图，重放时减少重复经过 Python／框架／runtime 的逐操作下发。**输入值可变，kernel 数量与单核 Duration 未必减少**；它不保证每个 Torch kernel 已最优，也不能把任意 Python 控制流一次录下永久执行。

- 触发第 3 步的稳定链／微空窗信号后，主动检查 CUDA／NPU 后端能力并做小对照，无需用户点名 graph。判定不适用时给出具体的动态状态、后端或成本证据，再考虑写核。
- 选**连贯、足够大的稳定片段**，可含 Norm → 变换／QDQ → Linear 及相邻逐元素操作，不限于自定义核。动态 cache 增长、I/O、停止控制可以留在图外，不强求全模型捕获。
- **数据相关路由不自动排除整段图**：先区分“值变化”和“shape／host 控制变化”。固定 shape 的 top-k、排序、计数、专家 QDQ／GMM 可连同共享分支试捕获，动态结果仍每步计算；用变路由输入验证。后端整数排序若落到 CPU，核对精确可表示的 device 排序键或现成路由接口；整段收益另行实测。实例见 [MoE 案例](references/case-moe-eval.md#2026-11-11glm47完整moe图用于缓存生成)。
- 已有 A／KV／MoE 小图或融合核、但同类空窗仍在时，沿输入到消费者检查相邻的 Norm、投影、残差和图间 copy，换成更大的稳定边界，避免盲目嵌套。整段下发是否解决看新 timeline。
- Graph 与 compile 分开判断：前者优先降低重复下发，后者还可能融合计算、减少中间量，取决于实际后端。两者可以组合，但跨 stream 或嵌套 capture 是否可行要实测；一次失败不能推广成“平台不支持”。
- 通过真实调用暖机，核对 shape／stride／dtype／device／stream 与执行上下文；暖机走真实 generate／decode，teacher、手造输入、prefill 只作补充。测量窗内不应有新的 capture／编译，冷成本单列。
- 用变输入验证数值、统计组、输出 alias／寿命与 cache 历史；输入地址固定时值仍会变。按调用者／stream 隔离持久状态；不为捕获关闭必要的 KV 或修改算法。
- 候选通过的条件：真实调用 host 更快、算法工作完整、冷成本可接受，代表性新 timeline 能解释变化。**随后回第 6 节重判剩余关键路径——首个提速不等于整轮完成。** 微小改动不必逐个重采。

具体接入与失败分支见 [graph-replay](references/graph-replay.md)。Graph 通常比手写融合核便宜，适合作为下发受限时的首个候选；收益与适配成本仍须实测。

## 5. 设备受限或框架方案不足：再选融合与kernel外援

- 先复用框架／厂商算子、批量组织、已有 kernel 或编译器融合，不要求全部试遍。只处理仍实占关键路径、能减少研究等待的热点。
- 区分三个收益来源：**减少下发次数、减少中间读写、改善设备执行**。融合可以同时贡献三者；单核 Event 快不证明模型快，也不能只凭 kernel 数选优。
- 需要手写时，交给 `kernel-knowledge`：真实完整片段、shape 族、dtype／stride／归约／mask、数值契约、当前最佳基线（含已验 graph）、频次和预算，并说明希望省哪段成本、为何框架方案不足。交接见 [kernel-decision](references/kernel-decision.md)。
- 专业 DSL 实现、设备计时、SOL 和 profile 由外援负责，本 skill 不另造迭代引擎。确需独立委派才用 `kernel-worker`；外援不可用时保留可信路径，不自动安装平台。
- 接回时计入包装、绑定、输入输出 copy、冷编译、buffer 寿命及 stream 依赖。局部快而真实调用无收益的候选不晋升，随即停止在它上面的投入。
- 候选通过的条件：与当前最佳路径同输入端到端对照，数值／覆盖通过且有维护价值；随后回第 6 节。单核或单阶段已快，其余主要阶段仍要检查。

## 6. 验收、回看与停止

- 同输入、同 warmup，少量交错复测（如 ABBA），保留原值和失败；小时级全量不为形式反复跑。单层、独立 graph／融合／流水线的倍数不能相乘，组合须在共同入口测。
- Host 计时包含真实输出消费，并在边界等待相关设备；加载、准备、冷编译与稳态分列。数值参考对照与生产暖机分开；混合测到的首轮成本如实标注，不全称作必要冷编译。一次性 JIT 不混入稳态，也不能从完整 eval 里悄悄删掉。padding token 不计有效吞吐。
- 实现按数值契约核对，评测另验身份／覆盖／cache 写读／官方评分；总分相同或有限 logits 不足以证明正确，跨 setting 答案不强求一致。图重放时 Python hook 不一定重跑，覆盖要用绑定／重放与实际目标任务互证。
- 训练验变输入、多步梯度、参数与 optimizer 状态，必要时验累积、随机性和跨 rank 一致性；涉及精度／有效 batch／loss 语义变化时另验收敛。完整训练 step 计入数据供给、反向、更新与通信，纯前向结果不能放行训练。
- 验收只认匹配源码／输入的新鲜日志、本轮实测及真实进程信息；启动成功、退出码、计时器、报告非空、残留的 completed 标记都不能单独证明完成。
- **每次实质优化后重判，最终交付前回看各主要阶段——首个提速不等于整轮完成。** 设备热点可能变成下发热点，decode 变快也可能暴露 prefill；据新证据选下一步。
- 对仍影响目标的主要成本，逐项交代：已处理／已验复用、具体不适用的依据、实测无净收益，或预算／授权／技术阻塞。“暂未做”不能写成“无优化空间”。有证据支持且预算内可行的下一步由 Agent 接着做，不留给用户追问。
- 多卡只作放置时不能宣称流水线；实施了重叠，就另验 stage 从串行到重叠、真实设备交叠与净吞吐，见 [multi-device-pipeline](references/multi-device-pipeline.md)。Graph 压的是阶段内下发，流水线处理的是独立工作的调度，两者不能互相替代。

**本轮只能从以下出口结束；候选通过后仍回到这里判断。**

| 出口 | 必须说明的证据 |
|---|---|
| 达标收口 | 真实调用及可靠性验收通过，实际等待满足约定目标；最后回看没有仍应处理的明显低成本浪费 |
| 阶段暂停，未达标 | 预算用尽、具体技术／授权阻塞，或有依据的下一步净收益不抵成本；列出当前差距、剩余候选及重开条件，不宣称已充分优化 |
| 用户明确停止／改目标 | 保存最快可靠路径、已验范围及未完成项，不继续扩大投入 |

交付时在现有记录里说清：**原关键路径 → 为何选此手段 → 实测改善 → 新关键路径 → 下一轮或停止依据**。一次推进负责到这个闭环，不留明显漏项让用户返工；它不承诺穷尽优化，也不新增管理表或工具矩阵。
