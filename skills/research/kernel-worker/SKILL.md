# Kernel Worker：有界委派，带证据交接

遵循 `goal-first`。主会话负责“为什么优化”、任务语义及最终接入；worker 负责约定范围内的候选与证据。加载本 skill 不会创建子 Agent：用宿主真实提供的、可编辑可执行的委派入口显式启动。

## 1. 满足独立性后派发

- 先由 `pytorch-perf-tuning` 确认热点；已有候选或简单改动能直接解决时不必委派。
- 固定参考计算、真实可重放输入、输出接口及数值标准。算法、统计组、舍入或状态语义未定时，先在主会话解决。
- 填写[任务brief](references/task-brief.md)，或引用能覆盖同等信息的现有任务记录。把本入口、brief 及相关资源的绝对路径传给 worker；worker 读不到主会话历史。
- 使用独立工作树／目录，记录基准 commit 或源码摘要；未提交的改动提供明确快照，不搬走用户的修改。列明可写文件、输出位置和唯一写入者。
- 分配设备及总预算，启动前核对实时占用——上下文和工作树隔离了，设备并没有隔离。总预算包含准备、编译、调优、验证和交付。
- 契约、环境和预算明确后即可按授权自主派发；新平台适配、语义变化或增预算回主会话决定。

完成：worker 可独立重放和判对错，不依赖隐含上下文，不与主线争用资源。

## 2. 核对任务与专业能力

- worker 读取 brief、参考源码与工作区规范，核对解释器、版本、输入、shape／dtype／stride、mask／分组、异常值域及必要的 backward／STE。先复用已有的同范围证据。
- 已有 `kernel-knowledge` 时，按[领域库入口](references/kernel-knowledge.md)定位当前源与平台技能，读取所需的工程／计量规范。它由用户按需安装。
- 库不可用但项目已有可信实现与工具时，可在相同契约内直接开发；缺少必需的专用能力时报告阻塞，不编造经验，也不自动安装平台。
- Atrex／KLineage 是可选外部能力。核对实际版本、目标后端与 evaluator：完整引擎能否运行以实测为准，参考资料支持某 DSL 只是前提。启动完整引擎时只由内部 Agent 写候选，外层 worker 负责适配与交付。

完成：有可信基线、可行执行路径和明确资源来源，或返回可操作的阻塞。

## 3. 守住实现与证据契约

- 不改参考、输入、误差阈值或计时器去迁就候选；不按输入值／指针硬编码答案，不跳过失败的 shape。
- 在范围内复用正确候选，按证据有界迭代；算法前处理与稳定原语分开，保留普通 PyTorch 接口与原厂高效库边界。具体优化方法由项目或领域库维护。
- 校验声明支持的真实负载、尾块、布局、统计轴、状态及梯度；有限校验不能推广到新模型／新版本。未支持的形态明确回退或报错。
- 与参考同输入、同环境、同口径交错比较，保留源码／配置与逐轮结果。计量合同写明窗口、预热、次数、统计量及并发依赖；plain、dummy、graph 各自报告，不混算倍数。
- 编译／准备成本与稳态分开，完整的冷启动成本如实保留。多流须正确汇合；收益以 host 端到端计时为准。
- 收益可靠且够用、停滞或预算耗尽时，返回最佳已验候选或参考，不自动扩到其他热点。正确性失败的候选不能标“可接入”。

完成：数值、支持范围和性能证据与本轮候选匹配。启动成功、进程结束或旧状态文件只是线索。

## 4. 后台生命周期与交付

- 按宿主机制后台启动并等待完成通知，不 sleep、不轮询；等待期间主会话只做独立工作。普通细节留在工作区，契约阻塞或异常退出及时返回。
- 超时／取消时核对本任务及其后代进程的状态，保存已验候选。worker 退出后，外部引擎／设备任务可能还在跑；只处理本任务的进程，不清理其他作业。
- 按 brief 返回候选位置、源码摘要、正确性与性能证据、未覆盖范围、接入方式、实际成本和停止原因。“可接入”只代表局部合同通过。
- 主会话核对证据与支持范围后接回 PyTorch，做必要的同输入数值与 host 端到端对照；通过 `exp-workflow` 已有的放行要求后再批量运行，复用有效记录。

## 5. 回流

- 委派遗漏、资源冲突、交接与成本问题更新本 skill；具体机器路径及运行状态留在项目／host 记录。
- 专业计量、平台实现和案例回独立领域库，按其当前入库规范发布；主体只同步必要摘要与引用，不维护第二份技术事实源。
- 首次 worker／外部引擎联动须做实用验收。
