# 真实踩坑与计算案例

来源：量化研究项目2026-11-10的GLM32短benchmark。下面保存可迁移条件与必要数值，不依赖原项目路径／会话／完整日志；它是单平台案例，不是所有模型的配方。

## 本例教训与迁移检查

| 症状／误判 | 识别与动作 | 不接受的结论 |
|---|---|---|
| 过去batch16跑得过，换一批prefill OOM | 先核最长真实提示、eager／融合attention及临时量；同batch的显存可随长度明显变化。保留全文，必要时改为较小完整batch并重测 | 固定batch就是容量保证；裁prompt后仍称同协议 |
| 前几批很快，随后allocated持续涨 | 同一进程比较每批同步后的allocated，固定shape复测；查活引用／cache／图buffer。回收仅做有界辨因，最终同路径计成本 | 每批重启掩盖问题；失败前快批次能证明全量可用 |
| reserved高，就断言泄漏 | 分开allocated、reserved、峰值与持久shape缓存；`empty_cache()`不会释放活引用，`gc.collect()`也不是所有增长的解法 | 回收后能跑证明已定位唯一根因／永久修复 |
| 打开Graph／fused配置后报收益 | 核实际重放、fallback、新capture与完整算法工作，真实generate暖机；尾批可能走不同路径 | 配置名就是实际加速覆盖；小模型smoke代替目标模型 |
| 预热很慢、后两轮快 | 分列首次JIT／capture／绑定和稳定wall；新shape可能继续付冷成本 | 冷成本可删；全量未见shape也能按全热态保证预算 |
| 迁移检查：第二轮接近零耗时 | 核是否命中旧响应／评分结果cache、是否实际forward；隔离结果cache后重测，正常请求去重／工件cache保留 | 把直接读旧答案称为模型热态吞吐；本例未发生此故障 |
| 复用prepared bundle，load字段只有几秒 | 外层独立记录checkpoint加载、工件应用／量化；内部字段可能只是适配和读数据 | 将内部load当全流程模型加载成本 |
| 少量选择题batch很密，外推异常快 | 复用完整请求，保留框架去重与等长尾桶，从真实完整作业抽样 | 用小样本重组出的batch密度代表全量 |
| seed和doc_id相同，但prompt对不上 | 检查样本顺序／映射与few-shot状态推进，直接核内容；可用完整规划请求抽样 | 同seed必定同prompt；历史全量成绩可直接配对 |
| 改max_new_tokens后很快 | 恢复原协议，跑完整生成；用实际步数与cap解释时间 | 16步teacher吞吐可直接承诺256预算的完整benchmark |
| 首轮减均值是1500秒 | 称首轮额外开销，查它包含的编译／数据／预热等；嵌套成本只计一次 | 全部都是纯编译；按每题放大所有固定开销 |
| 退出0，但有graph销毁ctx告警 | 独立核完整结果、数值／评分与覆盖；将退出清理和长期资源风险单列 | 结果不存在，或反过来“退出0所以长期无风险” |
| 短测脚本有拆批／回收，公共CLI没有 | 报告唯一已测入口与必需适配；后续全量需实际采用，再谈复用 | 其他同学裸跑公共CLI就一定获得同样时间 |

## 案例条件：不要搬走平台配方

- 模型：GLM-4-32B-0414；两张Ascend 910B2，分层驻留；CANN9.0、torch2.9／torch-npu2.9.0.post2、Transformers5.0、Triton-Ascend3.2.1、TileLang-Ascend0.1.1.10。
- 算法：HIF8伪量化，scale整数倍中心v4；融合SQ；W/A group128，W离线对称MSE选参，A逐投影动态规则；KV逐token/head 0.625σ，Q/P与GEMM仍BF16。
- 生成：真实HF／lm-eval，5-shot、greedy、256-token预算、2048上限；预填充TileLang、batch16 decode Graph。提示>1024时拆为两个完整batch8，其余batch16。
- 选择题：batch8、既有两卡threaded似然流水线及激活加速；没有把生成Graph用于无缓存似然。
- 没做两种零点的优劣比较。没有原生HIF8算术／8-bit缓存容量收益；这些数字不能外推到其他模型、SDK或后端。

## 失败与修正：有证据的部分才说定因

1. 直接batch16长提示prefill，申请4.49GiB时OOM；没有有效完整评分。
2. 长提示拆batch8后完成48／80题，但跨批allocated约31→36→43→50GB增长后再次OOM。不能据失败前的快批次宣称全量可用。
3. 新尝试只增加批次边界`gc.collect()`与`empty_cache()`，保留全部计算。完整80题通过，后续allocated回到约31.17／34.20GB，峰值约43.93／41.47GiB。
4. 这支持“回收措施使本短测不再累积”，不证明已查明所有保持引用的根因。Graph销毁仍有ctx告警；尾7、长期／并发稳定和全部新shape冷成本未设备验证。

拆批和回收只在该探针中，不在原公共CLI。未来模型应先辨因，不默认复制阈值1024、batch16／8或每批清缓存。

## 完整生成批次原值

固定seed42抽80题，实际分6批；另对batch8／16各做一次完整生成预热。

| 实际batch | 提示长度 | 实际生成步数 | 生成wall秒 |
|---:|---:|---:|---:|
| 8 | 1252 | 256 | 133.581603 |
| 8 | 1252 | 192 | 100.709576 |
| 16 | 1019 | 256 | 80.574887 |
| 16 | 913 | 256 | 80.039440 |
| 16 | 822 | 187 | 58.858023 |
| 16 | 763 | 199 | 79.057506 |

- 生成合计532.821035秒；评分801.541726秒，其中额外预热245.413233秒，其余评分／回收23.307458秒。后者不是纯GC时间。
- 80题／160条双filter官方重放通过；366个Linear和61层KV覆盖，Q/P未量化，segment／KV各140,422次实际图重放。小样本分数不作新精度结论。
- 当前框架CPU规划完整1,319题后得到22个batch8、71个batch16及尾7；按类别重加权的纯生成约2.22小时，而按题数为2.44小时。两者差异来自实际批次构成和生成长度，均不是精确全量答案；该次预算采用后者并披露盲区。

## 合计怎么算，哪些没有测

$$\widehat T_{\mathrm{GSM}}=(532.821035+23.307458)\frac{1319}{80}\approx9169.17\ \mathrm{s}.$$

$$\widehat T_{\mathrm{eight}}=\sum_j\frac{t_{j,1}+t_{j,2}}2\frac{J_j}{16}=8106.65\ \mathrm{s}.$$

八项完整请求读取／分词实测137.228090秒，加入后九项46,908题热态外推：

$$\widehat T_{\mathrm{nine,warm}}\approx9169.17+8106.65+137.23=17413.05\ \mathrm{s}=4.837\ \mathrm{h}.$$

额外已测：冻结准备／加载／预检268.343833秒；生成预热245.413233秒；八项首轮减稳态合计1503.684064秒。

$$\widehat T_{\mathrm{known,start}}=4.836958+\frac{268.343833+245.413233+1503.684064}{3600}\approx5.397\ \mathrm{h}.$$

- 全量未见shape的JIT／capture、完整建请求／汇总和长期资源问题未闭合，故最终为**约5.40小时＋未覆盖成本**，不是首次冷启动上界，不证明≤5小时。
- 双轮快／慢值对应九项4.790～4.884小时，仅为同样本计时包络；不是采样置信区间。
- 成功探针约50.08分钟，含两轮重复测量和全部首轮开销；不是模型全量时间。早期失败也不作为正常启动成本混入最终估计。
