# 抽样、计时与外推细则

本页处理不同模型的工作量差异；不规定模型加速手段。先按`pytorch-perf-tuning`选定已有可靠路径，再使用本页计算。

## 1. 单位跟评测器走

| 路径 | 原始单位 | 更接近成本的单位 | 常见错算 |
|---|---|---|---|
| 多项选择／似然 | 题、选项请求 | 去重／分桶后的完整forward作业 | 默认每题4次forward，或忽略同上下文缓存 |
| 自回归生成 | 问题／请求 | 完整生成batch，提示长度与批内最大decode步数 | 单题token均值乘批次数，忽略EOS／padding |
| 跨卡流水线 | 完整batch序列 | 真实并发调度下的连续作业块wall | 累加两卡耗时，或用串行样本预测流水吞吐 |
| 多进程／多副本 | 分片／rank | 最慢分片及协调的真实总wall | 把所有rank时间相加，或假定理想卡数倍加速 |

同一task名不保证提示或请求相同；模板、few-shot种子／采样序列、tokenizer、版本和是否chat会改变真实工作。

区分三类cache：请求／分词与工件／编译cache按目标冷暖场景复用；框架正常上下文去重保持；会直接返回旧响应或旧分数、绕过模型的结果cache必须隔离。重复计时的每一轮均核实际模型调用数，不能以文件有输出证明真的算了。

### 完整请求规划

1. 复用实际任务配置和框架，CPU构建真实请求；必要时读取同协议保存的请求。不加载第二份模型来数题。
2. 按实际tokenization、上下文缓存、去重、排序、分桶、batch上限及尾批生成作业计划。数据中的官方重复题保留题次权重；框架自身的请求去重另计。
3. 把生成／似然、模型版本、执行setting不同的工作分开，不能用已有似然吞吐预测新生成路径。
4. 只做一次足够的规划并复用。构建全量请求本身昂贵时按任务流式处理；无法精确规划则记录抽样估计和缺口，不假装有精确`J_h`。

完成判据：完整题数、原始请求数和模型作业数关系明确。

### 子集身份与few-shot陷阱

- 部分harness按数据集顺序取文档，却按传入列表回填`doc_id`；显式索引先排序，核实际doc／prompt／target，而非只信编号。
- 同一个seed不保证子集与全量few-shot一致：抽样器的随机状态可能随文档访问次数推进。最直接是复用全量规划里的实际请求；若使用框架原生子集重建提示，保留其行为并披露差异。
- 不能只按子集文档重算prompt长度却称全量batch计划。应以实际完整请求规划；CPU规划全量不等于执行模型全量。
- 没有明确逐位／同文本契约时，不要求不同batch／后端setting的logits或答案相同；检查本setting算法实现与评分有效性，不混旧setting基线。

## 2. 少量分层，不造全shape矩阵

先找造成成本差异的少数因素：任务形态、提示长度、实际batch、decode步数、必要的路由／后端分支。共同分布的学科可合并，不给MMLU每个叶子强制分配一轮。

一个可用起点：将按长度排序的完整作业分成四个等作业数区间，各随机抽少量完整作业；高风险最长提示、尾批／图回退另作边界核验。数值只作起点，按预算与实际差异选样，不固定80题或16作业。

- 主体用无偏抽样或已知权重的分层抽样；边界样本不直接等权混入主体均值。
- 每层`m_h`应是不同作业数；同16作业计两轮，仍是`m_h=16、R=2`，不是32个独立样本。
- 不同层全量大小不同，使用各自`J_h/m_h`，不能平均各层秒数后乘全量。只有各层抽样率相同时，才可合块按总比例放大。
- 短流水线块反复包含填充／排空；full只发生一次的部分不能按块数放大。若未独立分出，保留这种估计偏差，不凭经验扣秒。
- 一次命中最长提示只证明该输入的容量；连续批次和固定shape复测用来识别累积。不同shape持久缓存增长与同类批次重复泄漏分开判断。

完成判据：样本保留真实调度、各层权重正确，主体估计不被人为加密batch或极端样本扭曲。

## 3. 两类计时不要混

**端到端预算锚**：实际评测入口的host wall，包含真实工作、必要等待和输出落地。分解用批次／阶段计时，不能把分解重叠段直接相加。

**稳态块**：真实入口暖机后，在连续作业块边界同步参与设备，再用单调时钟测完成及输出消费。不使用单kernel Event、dummy填队列或累计kernel Duration作为benchmark总耗时。

可以用已有日志／计时钩子，只有缺字段时才加任务内最小记录；不为此写通用运行引擎。逐批记录的最小信息：输入shape、实际batch、生成步数／cap、wall、边界显存；阶段另存是否发生JIT／capture及冷／暖上下文。

检查两轮：

- 同样本后轮稳定且内存平稳：可形成条件化均值，保留原值。
- 持续漂移／慢批：核新shape、编译、路由、生成长度、同步、外部负载和回收；不直接删掉异常轮。
- 每批都遇到新shape：可能没有可复用稳态。可分别给热态能力与真实冷运行预算缺口，不能据热态独自回答首次完整运行。

## 4. 总时间的三种含义

令`S`为分层得到的评分wall估计，`D`为未包含在`S`中的数据／结果处理，`L`为实际加载，`P`为准备，`W`为独立计量的冷建／暖机：

| 场景 | 可报告的式子 | 不能省掉的条件 |
|---|---|---|
| 模型与所需shape已暖好 | `S + D` | 仍包含正常回收、同步与评分；不是纯模型设备时间 |
| 已有量化／校准／编译工件，启动新进程 | `L + P_replay + W_process + S + D` | 磁盘cache命中不等于进程内图／绑定已建立 |
| 真正首次启动 | `L + P_build + W_observed + S + D + U_new` | `U_new`含全量未覆盖shape／分支的JIT、capture及准备缺口 |

下载、校准、离线选参、工件写盘若在用户要的范围内也应计量；若复用则明确“未包含重新生成”。多次独立装载按正式启动次数加，不把多个历史run的准备机械相加成一次联合评测。

**只加没有重叠、没有已计入其他wall的项。** Graph内部`cold_seconds`已在额外预热时间里时，不再加一次；完整eval内计入的安全forward／准备也不能同时再加到总wall。

### 正确处理冷shape

- 登记本次实测的shape／版本／编译缓存状态与首次额外成本，不默认跨机器、版本或源码位置缓存仍命中。
- 全量计划若有未暖shape，明确数量／类型和是否走回退；未测成本写成`U_new`，不写0，不把已测冷开销之和称完整上界。
- 只有预算允许且已获授权，才做少量新shape冷成本抽样或预构建；不要为一个时间估计自动编译全量shape。
- 可从新shape样本估计额外成本，但须给抽样／权重和误差来源；不能简单将“首轮−稳态”全称编译后按题数放大。

## 5. 精度、区间与交付

- 均值反映本次稳定块；双轮快／慢值可给计时波动包络，**不是采样置信区间**。
- 规划范围应说明最敏感假设：输出长度／cap比例、长提示batch构成、尾批回退、新shape编译、设备共享。没有证据就留未知，不用固定加20%伪装覆盖风险。
- 若两种合理权重法给出不同估计，并列解释差异；不能取更快的就称更精确，也不能把更慢的自动当数学上界。
- 预算问题已能回答就停止。尚未能得到可靠总量时，先交可用的部分估计与阻塞，不报一个假精确的总数。

在现有报告中用以下最小结构即可：

```text
结论：模型／选定路径；热态预计X；已有工件重启预计Y；首次冷启动Z＋未覆盖成本
实测：哪些任务／题／完整作业，暖机与计时轮次，连续批内存与覆盖
计算：每层J、m、各轮t，公式，固定成本和哪些字段重叠
边界：非全量实测；区间代表什么；未测成本与采用路径的限制
复用：原始结果和唯一运行入口；源码／配置变化后只补受影响部分
```
