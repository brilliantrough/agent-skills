# 从项目经验提炼知识库

目标：让另一个项目的Agent知道先做什么、什么方法值得试、典型数值和成本怎样、哪些地方不能想当然。

适用于开发、科研、性能与工具项目；不限定领域或知识深度。只用已有证据：整理知识库不重跑实验，也不扩研究范围。

知识内容、skill使用入口、维护仓库是不同层次。先分清**可执行流程**与**参考知识**：共享核心合同写入对应 skill 主体，参考知识放 kb／reference 按需查阅；分支专用流程可随对应 reference，但主体必须写明何时读取，进入该分支后同样必须执行。来自经验总结的共享核心流程照样进主体。交付形式可以是更新现有kb-*、补反例/适用条件，或向独立领域库交付，新建skill只是其中一种。已在领域流程内完成选材与验收时，直接遵循目标库当前规范，跳过通用筛选和确认。

## 1. 找到值得迁移的材料

- 从用户目标、当前交付和已有知识库入手；先找真实维护源，能补现有kb-*或独立领域库就不另建重叠库。历史快照、安装副本与当前源分开，技术事实只改当前维护源。
- 用`load-mem`回收相关背景，按线索查报告、配置、结果表、决策、journal、Git和历史消息；有记忆工具时主动查真实踩坑与更正；README和最终成功报告只是其中一部分。
- 旧Agent标出的“必须记住／不要再犯／已撤销”是高价值线索，直接提取其已有证据。
- 这些标记是线索：重要数字、配置和修复要找到对应结果或当前记录，才算确认因果和当前有效。旧错误保留为反例，更正另标清楚。
- 沿相关线索补齐即可，不必每个记忆系统都搜一轮。缺来源或资料不可访问，标明缺口。
- 外部资料有用则连同固定版本、出处与原文/许可条件保留；外部报告与本项目复现分开标注。

完成标志：已找到能指导相似任务的材料及来源，也知道哪些只是状态、猜测或已失效记录。

## 2. 判断价值，不按篇幅或新奇程度筛

核心问题：**拿掉这条，下一位Agent是否容易选错、漏条件、估错收益/成本，或重踩已发生的坑？**

| 候选内容 | 保留建议 |
|---|---|
| 重复流程、触发条件、先后顺序、强制检查与交接 | 优先进入流程性 skill 主体，写成明确的执行合同 |
| 有效方法、关键决策及适用/失效条件 | 优先；解释何时选、为何选、何时停止或换路 |
| 经典结果、完整配置、经验范围、离线/在线成本 | 优先；带baseline、协议、单位和证据，连同非最优结果 |
| 阴性结果、不起效的组合、已纠正的错误解释 | 优先；能省下重复尝试或约束结论，就是经验 |
| 已真实踩过的坑、反直觉现象、易混轴/键名/接口行为 | 优先；即使概念简单或只发生一次，也可很昂贵 |
| 基础知识 | 能防真实误用、或读懂后续配置所必需时简写；否则略过 |
| 待验证猜测 | 有明确后续判断价值才留，单列为未验证 |
| 进程/PID、临时目录、一次性操作流水 | 留在项目记忆；只提炼可迁移教训 |
| 无差异点的常识、重复记录、无用途的碎片 | 合并或舍弃 |

- 有价值的长尾放reference；条件、反例和经典数值即使入口要短也保留。
- “历史被记过”是优先线索；合并重复项，核对更正，保留可操作细节。
- 项目特定的内容也能迁移：模型/硬件/版本作为案例条件保留；个人路径、身份、凭据和运行状态留在原项目。
- 一个案例是经验锚点；同条件重复或多例支持后，才谈范围和趋势。机制事实、实测、推断分别写。

完成标志：每个建议保留的主题都有用途与具体内容；每项舍弃都有具体理由，“太基础”“只出现一次”这类说法需要换成具体理由。

## 3. 给建议，让用户补漏确认

成库之前，先在聊天里给一轮按主题合并的短清单：

| 建议主题 | 拟保留的具体经验/数值/配置 | 迁移价值与证据边界 |
|---|---|---|
| 已验方法与结果 | 代表配方、相对基线、成本、失效组合 | 给新任务选路与估预期；标明验证范围 |
| 真实踩坑与诊断 | 症状→根因/未知→修正→复验 | 防止重踩，保留容易想当然的细节 |
| 配置与参考 | 最小有效配置、关键开关、外部资料 | 能照着开始 |

表格只是结构示意，填入项目的真实内容。简短列出建议不带走的内容和重要缺口。

- 流程性内容同时确认写入哪个 skill 主体、触发后必须完成什么；参考知识说明适用条件与出处。
- 给明确推荐；通常只问一句：“建议保留这些。哪些要删，哪些重要经验我漏了？”
- 等用户确认、删补或明确委托你判断后，再成库；用户没有回应时继续等。
- 用户已明确选定材料/范围时复用该确认。新出现的范围、敏感资料或影响结论的缺口再讨论。
- 用户补充的经历也标来源与证据等级；用户认可的结论仍按其实测状态标注。

完成标志：保留主题与范围已对齐，用户有实际补漏机会；普通命名、排版和拆文件由Agent决定。

## 4. 按目标维护源交付

- 交付为skill时加载`writing-skill`，按命名、description、短入口与附属文件规则组织；文字遵循`readable-docs`。
- **共享核心流程必须进主体**：其触发、阶段顺序、必须／禁止、完成判据、衔接操作与失守处理写进 `SKILL.md`，用明确命令句。任务匹配后它就是执行合同：共享核心流程留在主体；分支专用流程可随对应 reference 按需加载，主体必须写明何时读取，读取后同样必须执行。纯知识与分支专用细节可放 reference，主体指定读取的 reference、指定触发的操作同样是合同的一部分。
- 已有独立领域库时，先读其当前入库、证据和发布规范；例如kernel经验进入`kernel-knowledge`，主体只留入口。领域验收和schema以该库规范为准。
- 已确认的选材与已有有效验收直接复用；只有新增范围、敏感资料或关键证据缺口才再问。

以下是内容完整性检查；文件布局沿用目标库：

- 入口面向新任务：何时用、第一步查什么、如何选路、哪些误用先排查、何时转其他skill。
- reference按需容纳经验规律、成功/失败路径、诊断与外部证据；完整配置、可计算表格和必要小样本放assets；目录按实际内容设，不必凑齐。
- 数值随比较合同保存：对象/版本、算法与关键配置、baseline、数据/样本/种子、指标/单位、结果和适用边界；性能另带硬件、负载、计时范围与成本。
- 不同比较组分开；粒度、后端、样本或预处理同时变化，称组合结果。缺字段标未知。
- 踩坑写到能行动：什么症状、错在哪、如何识别/修正、怎样验过；根因未明就保留未知。
- 除了“做什么”，还要保留关键先后顺序、参数关系、正确广播/归约轴、共享分支、缓存失效等真正易错条件。
- 相对引用要落到随包文件；关键理解要能脱离本机路径、私有会话或记忆ID读懂。原始大工件可留项目，库内保留必要摘要、出处与未打包边界。

完成标志：新Agent不依赖原会话也能据此开始相似任务，并知道触发后必须执行哪些步骤、调用哪些操作；经验仍带着各自的条件。

## 5. 用真实案例走读，再交付

- 选已有代表性案例走一遍入口：能找到起步配置、预期量级、已知反例和诊断路径；无需重跑原实验。
- 再用第二次触发的话术走读执行权威：Agent 必须先读主体，把强制项纳入计划／todo，在指定时点调用其他操作，并在交付前核对。若读完只得到“可参考”的背景知识，本次流程性 skill 交付不通过。
- 抽查重要数值及配置与原记录一致，失败/撤销项不再作为正面证据。skill能加载只说明格式可用，内容正确性和跨项目效果另行标注验证状态。
- skill交付按`writing-skill`检查触发与格式，其他条目按目标库规范；都核对引用、去情境化和可分发性，凭据不随包。
- 在约定位置交付整目录，按需附迁移包；更新已有库时保留用户修改和证据演变，不认识的内容保持原样。
- 告知维护源、交付位置、覆盖、未核实/未打包内容及发布状态即可。新实验和更大的知识体系需要用户另行提出。
- 使用后发现失效、遗漏或更强证据，回该维护源补条件、反例或更正，再按其规则发布；引用端复核摘要即可。

完成标志：内容、可移植性与实际交付均已检查；未验证边界诚实保留。

## 维护

本流程只随真实漏筛、过筛、遗漏或误迁移反馈做小修；具体领域经验回目标kb-*或独立库。
