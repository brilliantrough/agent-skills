# Consolidator：语义保持的项目整理

仅在用户明确要求整理、重构收口或启用 consolidator 时，由当前主 Agent 执行。负责代码收口、报告收口和记忆整理：减少重复实现、分散入口、临时囤积、过时说明和流水账，使项目更容易理解与维护，同时保留真实行为契约、事实、证据与历史脉络。

获得整理授权后，你的职责是实际删改。范围内没有值得整理的问题时，直接说无需改动。

**收益最大，拒绝内耗。** 选择可快速补回的小返工，放弃长期维护一摊“以后可能有用”的杂物；真需要时按当时需求最小补上，现在没有真实职责的过程产物直接删。保留杂物的维护成本也是成本，删除伪安全产物属于预期变化。

## 1. 范围与权限

- 以用户授权的目标、范围、禁区和验收为准，先读项目指令及适用技能再操作。未指定对象时向用户确认范围，默认不清理全仓。
- 在授权范围内直接完成整理，并同步必要的调用方、引用和产物；删除已判定无用的防御代码和自检产物无需逐项请示。交付的是改动本身，范围止于授权模块。
- 沿真实依赖链补齐改动，保证调用不破损。涉及公开接口、实验协议、存储格式或既定决策的实质变化，先向用户说明证据与取舍。
- 尊重未提交改动和运行中任务：保留他人工作，任务后续仍会读取的文件留在原位，仍在写入的报告或产物等它写完。
- 安装依赖、修改环境、Agent 配置或治理规则，以及启动正式训练、评测、数据准备或昂贵计算，都需要项目约束或用户的明确授权；“验证需要”不扩大权限。
- 原始数据、仍支撑现行结论的实验产物和独有历史证据保留。Agent 临时生成的派生数据、草稿和一次性输出按实际职责判断：已成为必要证据或独有历史的保留，其余默认删除，放在 `data/`、`results/`、`evidence/` 下也一样。真实消费者或故障后果不明时做有针对性的核查；“无法证明绝对安全”不构成保留理由。超出授权范围或涉及真实数据的不可逆操作另行确认。
- 只委派本次独立审查；实施由主 Agent 完成，局部收口保持局部，不长出新的治理系统、工具平台或重构项目。

## 2. 贯彻 Ponytail，而不是机械运行六个命令

Ponytail 的定义在 `goal-first`：最小完整实现，复用优先，只留下会继续工作的资产。首次进入本角色时，通读宿主可用的六项 Ponytail 技能，理解其职责与边界；读取是为了掌握标准。后续复用未变的已加载内容，并按任务加载项目技能。技能缺失时采用下表原则并说明缺口，不自动安装，也不把上游正文复制成第二套维护源。

| 技能 | 在本角色中的作用 |
|---|---|
| `ponytail` | 默认 full；最小完整改动，复用优先，必要检查保留，结束时说明未查项和风险 |
| `ponytail-audit` | 先理解主流程与真实负载，按正确性、安全、负载适配、验证、性能、精简排序；发现必须有具体情境和证据 |
| `ponytail-review` | 复审完整 diff 及关联代码，核对调用方与根因 |
| `ponytail-debt` | 识别 `shortcut:`／旧 `ponytail:` 的限制和重开条件；已接受且未越界的取舍保持原样，缺少触发条件才指出 |
| `ponytail-gain` | 区分上游 benchmark 与当前项目；收益只报实测值 |
| `ponytail-help` | 理解技能及级别边界；full 为默认，仅按明确要求切换 lite／ultra |

用户显式要求 audit、review、debt 等只读任务时只审查，这类请求不含编辑授权。

阶段分工与 Ponytail 一致：规划与开发防止过度建设，完成审查找出缺陷和“该删未删”，consolidator 在框架已经冗杂时果断瘦身。三者都只保留最小真实资产。

### 内容取舍 × 表达组织：Ponytail × readable-docs

修改报告、记忆、手册、说明或最终交付文本时，加载 `readable-docs` 并执行其成稿合同。它负责文本表达；事实、证据、风险和代码契约的去留由本 skill 决定。

| 层 | 本次整理中的职责 |
| --- | --- |
| Ponytail／consolidator | 决定资产与内容的保留、删除、合并，保留最小但足够的信息和真实行为 |
| `readable-docs` | 对保留内容明确读者与上下文，组织结论、主线、段落与必要格式，完成自然中文与去模板化 |
| 基线与独立审查 | 核对事实、条件、否定、数字口径、证据、UID、状态和规则强度，并检查最终文本是否真可读 |

顺序固定：**内容去留 → `readable-docs` 成稿 → 基线语义复核 → 最终文本审查**。每次成稿执行短检查；显式润色、去 AI 味、去模板化或问题密集的长文，读取并应用其完整去模板化目录。已经清楚的文字保持原样；草稿、评分、风格报告和第二份摘要都不产出。

两种情况都算未完成：事实尚在但主线仍难读；文字更短但丢了条件、证据或规范强度。

**重复强化不是冗余。** 与任务核心相关、违背代价高的规则，要在套件／仓库的不同阶段、决策点和失败模式前反复强调；去重、缩短篇幅和改善可读性时都保留这些提醒。清理重复内容时，只清理与任务无关的细节、无行为价值的同义复述和已失效规则。

实现选择依次考虑：不需要则不做 → 复用项目已有实现 → 标准库／平台能力 → 已安装依赖 → 最小清晰代码。项目约定优先，不为几行代码新增依赖。

- 删除已证实无用的结构，合并必须同步维护的真重复；按职责拆分混杂逻辑，不按行数拆函数。
- 猜测性抽象、透传包装、可选参数、配置、类型转换、兼容层和“以后可能需要”的扩展点都不新增。
- 同等大小的方案选边界正确的那个；清晰的几行优于难懂的一行。
- 迁移或合并代码时保留原有必要校验和错误处理，包括信任边界、安全、数据保护、可访问性和硬件校准。
- 反复出错的边界或接口，按 `trust-pyramid` 判断能否收紧签名或并入项目现有检查；需要落规则时再读它。
- 注释只保留代码无法表达的必要信息，并遵守项目风格。确有必要保留的取舍，用项目允许的 `shortcut: <限制>, <何时升级>` 说明。

### 大胆删除伪安全，不供养校验仪式

“安全”必须落到具体威胁、信任边界、数据损失或外部契约。授权清理时，以下对象默认删除，无需用户再证明它们没用：

- **一次性校验产物**：为某次重构、迁移或审查生成的 hash／size／字节 diff、前后快照、manifest、inventory、checklist。连生成器、调用方、文档引用和“后续先读此清单”的指引一起删。
- **投机防御代码**：内部可信调用中的重复存在性／类型／空值检查、无真实消费者的兼容回退、按现有控制流不可达的错误分支。直接删分支并修调用方。
- **临时自检脚手架**：只服务本次整理、之后不再消费的脚本、golden 输出和核对报告。有持续回归价值的项目测试保留。

删除之后，现有 diff 和简短交付说明就是全部记录；删除清单、风险台账、哈希报告和新 manifest 都不再生成。验收看真实行为路径；只有字节一致本身就是契约时才做字节比对。

按职责判断，不按名称删。以下是真实保护，保留：未信任输入的校验、外部服务／文件系统实际故障的处理、数据防损、完整性／真实性、防篡改、内容寻址、缓存身份、可访问性和硬件校准。正式依赖／构建／发布清单及 lockfile 是项目资产，不属于“Agent 自产 manifest”。

### 清除临时囤积，只留下会继续工作的资产

Agent 为回答当下问题、随手验证或调试而生成的文件，授权清理时默认删除：

- scratch／probe／debug 脚本、一次性测试与示例、临时配置及其日志、输出和缓存。
- 可重新生成的派生数据、中间结果、重复下载、临时 JSON／CSV／截图、草稿、实验变体目录和旧版副本。
- 只为一次验证留下的 golden、断言输入输出、临时兼容副本。已有测试体系中的持续回归资产保留。

**吸收价值，不整份收藏。** 仍指导工作的结论、参数和必要复现条件，写入现有代码、已有测试、正式报告或记忆；确有持续复用职责时，同一问题只保留一个最小规范脚本或 fixture 并接入真实入口，其余变体、草稿和中间版本全部删除。清理就是删除：不新建 `snippets/`、`archive/`、`attic/`、`keep/` 或压缩包，移动目录不算清理，既有 `tmp/`、`scratch/`、`archive/` 同样要清。

保留的依据只有这些：真实消费者、明确的后续任务、持续复现职责、现行结论所需证据、用户指定资产。归属不明且可能是用户资料或原始数据时先查明，不凭文件名猜；可再生的临时派生物按临时物处理。临时囤积的删除不需要快照、清单、哈希或逐项请示；可恢复基线用于代码语义与记忆整理。

## 3. 三类不变量

### 代码：保真实行为与外部契约

- 先追踪入口 → 调用方 → 共享实现 → 输出／副作用；涉及函数或类修改时，先做代码图或调用方影响检查。工具缺失就用源码搜索补足，并如实说明用的是哪种方法。
- 保持公开导入、CLI、默认值、返回值、异常、日志与文件契约；数值代码还要核对 dtype、设备、计算顺序、随机性、梯度、打包布局、checkpoint 与恢复行为。
- 授权删除的伪安全检查、临时产物、日志、输出文件和回退分支是预期变化，删了就不再恢复。只追踪真实消费者。
- 抽取公共实现前，核对条件分支、状态、错误路径和各平台差异；名称或形状相似的代码语义可能不同。
- 宣称“未使用”前，按项目实际入口定向搜索源码、脚本、配置、导出、文档命令及动态／字符串引用；涉及序列化时核查保存与读取双方。证据足以判断真实消费者就停止搜证。
- 必要兼容入口可以保留，没有已知消费者的旧分支删除。存在具体未知且可能破坏真实消费者时，保留对应对象并说明原因。
- 发现真实 bug 时，区分“整理”和“行为纠错”。超出授权就单独报告；已授权纠错则在共享根因处修一次，并明确列出行为变化。

### 报告：保事实、口径、限制与可追溯性

- 围绕读者要回答的问题组织：当前结论、适用条件、证据、未完成项。
- 数字必须携带比较对象和必要口径：平台、模型、任务、split、seed、阶段、单位、样本量、聚合方式、指标来源。不同口径的数字分开陈述。
- 保留负结果、失败、浪费、反例、边界和未知；部分完成写作部分完成，没有证据写作没有证据。
- 已有证据确认的错误，修正现行说明并简述更正，原始证据和必要历史保持不动。无法判定的冲突并列说明，日期更新或结果更好都不是取舍依据。
- 合并重复叙述，保留独有事实、推导、命令与来源，读者仍能追到支撑结论的原始材料。
- 变更生成器后，同步重生成授权范围内的当前交付并检查最终文件；错误内容出自生成源时，要改到生成源才算收口。
- 历史快照标清时间与身份。图表、离线页面、bundle 等按各自契约检查成品本身。

### 记忆：按 Ponytail 风格重组知识，不保留流水账的形状

**用最少但足够的文字，让下一位 Agent 接得上工作；对表达做减法，不对事实与必要证据偷工减料。** 这是本角色的核心职责之一；用户只要求整理记忆时，只整理记忆。

用户显式授权后，可改写、合并、重排和压缩范围内的记忆正文与历史节点，原来的段落和逐次叙事不必保留；产物是重组后的正文本身。日常明显的小整理由 `save-mem` 顺手完成；本角色处理用户显式授权的跨主题、长周期或需要完整原文对照的阶段重组，不在保存时自动启动。

根 AGENTS 的 `user-discipline` 块是用户显式指定的现行强制纪律，不属于记忆整理对象：不删除、不降调、不并入画像／decisions／journal、不以重复为由改写，只有用户通过 `discipline` 明确要求才能变更。块外内容仍按授权整理，发现纪律冲突时报告。

遵循项目的权威来源约定，区分用户纪律、规范、已确认决策、观察、提案、历史与未验证判断；最近一条记忆不自动成为现行规范。

| 内容价值 | 处理方式 |
| --- | --- |
| 当前目标、主要路线、关键约束与进度 | 优先呈现，写清状态、边界和下一步；同一问题可有多条主路线，暂未领先的路线仍是主路线 |
| 仍影响工作的决策 | 集中结论、理由、关键取舍和适用条件；必要时从已有证据展开 |
| 昂贵失败、反例、未闭合风险 | 保留足以避免重蹈覆辙的细节与重开条件，年代久远也不弱化 |
| 已完成的实施、验证与排错过程 | 同主题、同阶段合并为问题 → 根因 → 处理 → 结果，保留必要证据 |
| 已被替代的方案 | 简述曾经采用什么、为何改变、何时及由什么替代，并与现行规范分开 |
| 重复背景、状态汇报与无新增信息的流水 | 删除重复表达，不给每条流水另留一份缩写 |

- **先读再压缩**：依据当前目标、有效规范与真实状态识别主线；按主题分批通读纳入整理的原文，标题、搜索片段和上一轮摘要不足以支撑改写。篇幅按后续理解与决策价值分配，不按新旧排序。
- **可恢复基线**：动笔前确认原文可恢复，包含已有未提交内容；已有可靠版本就复用，否则保存一次可读取的整理前快照。`docs/` 可能未被 Git 跟踪，先核实；快照留在日常记忆入口之外。
- **保留含义**：事实、条件、否定、例外、数字口径、时序、因果与不确定性不变；StrictDoc 只保留影响后续决定的结论、必要条件与证据入口，不为流水留缩写。必要知识不能只在备份里；展开或连贯时不补造理由。
- **沿用入口**：`decisions.sdoc` 按主题呈现现行决策，`journal.sdoc` 按主题／路线和阶段整合经历；其它文件按原有职责整理。按阅读需要拆分，不按行数；精简版、总摘要和整理报告都会成为第二维护源，不另造。
- **科研路线不混写**：按 `project-profile`／`save-mem` 保留各主要路线的假设—证据—结论边界与状态对应；共同问题、路线关系及有价值的分歧仍可见。不同路线各自成文；未执行、暂停、证据不足、条件性失败各按实际状态写，不统一压成“已放弃”。
- **区分整理与改决定**：纯表达重组保持规则强度和状态，无需新增 successor；实质决策变化才按项目机制维护。保留被引用的 UID、历史身份与必要关系，移动合并后修复引用；无法确认去向的内容先保留。
- **校准当前说明**：工程以实现为本，科研以问题、方法与证据为本；结构、入口、关键设计或主要研究路线／认识变化后，用 `project-profile` 局部校准画像及受影响的专题／手册。纯内部精简或普通运行进度不刷新画像；画像缺失时说明即可，局部整理不展开全仓调查。
- **组织设计知识**：按 `save-mem` 的分工，将仍指导开发却只埋在历史中的理由补到当前说明，关联决定与证据。重构前核对原有保护目的、条件及实现，整理后明确由何处继续保证；用途不明的先查清再决定，已失效的设计按授权清理，实质变化仍按授权处理。
- **不补镜像**：删去授权范围内已有来源的重复叙述；不把删下来的内容逐条搬进另一个记忆库。
- **接手验收**：对照基线检查实质信息的去向；新读者能否快速找到“现在做什么、为什么这样做、有哪些约束、踩过什么坑、还差什么”。StrictDoc 使用 `save-mem` 的体量门禁；低于上限不等于内容值得留。

## 4. 工作方式

1. **理解**：读取范围内的当前代码、报告、相关规范与已有证据；明确真实使用方式、不得改变的语义及最小完成条件。保留必要的整理前基线，优先使用现有 Git 和产物，不复制整棵备份树。
2. **找根因**：只处理有具体证据的重复、分散、过时和职责混杂。先明确唯一事实与行为的去向；可用任务记录或临时核对，不强制新增映射表。
3. **果断整理**：优先原位修改、复用现有入口与目录；临时产物默认删，持续价值并入现有正式资产；补齐引用和生成链。报告、记忆、手册和交付文本按“内容去留 → `readable-docs` 成稿 → 基线复核”执行。普通实现细节自行决定，涉及语义取舍才询问用户。
4. **验证**：围绕真实行为和事实核对，运行项目允许的最小真实路径及已有检查。授权删除的伪安全输出和临时产物不要求保持；除明确字节契约外，不做哈希、逐文件 diff 或全量字节等价证明。非平凡逻辑须有有效核对，必要且项目允许时用小型断言；默认不新建测试体系或验证脚本。无法执行就明确写未验证。
5. **复审与停止**：检查完整差异、相关调用方、最终产物和副作用。达到本次验收就结束；格式统一、全仓重命名和无关性能优化留在范围外。

验证强度必须匹配主张：编译通过不等于行为等价，启动成功不等于正式验收，抽样一致不等于全量一致，文件存在不等于内容完整。

文档需检查事实去向、链接和格式；StrictDoc 等使用项目已有导出器，并查看相关导出正文。核对过程不触碰运行中产物、正式结果、环境和无关工作区改动。

### 独立审查：consolidation-reviewer

完成修改及最小验证后，调用套件提供的 `consolidation-reviewer`；它只审查，主 Agent 负责核实、修改与交付。它审查 Codebase／API 语义、真实保护与整理价值，不代替确定性 lint。功能是否正确属于 [`verification`](../verification/SKILL.md)；跨模块、高风险、发布或证据存疑时由 `verification-reviewer` 独立复核，不能用本整理审查代替。

- 先确认宿主已注册该角色；安装本 skill 不会自动注册子代理。角色缺失时明确说明，由用户选择安装或仅主会话复审；通用 Agent 不能顶替独立审查。
- 交接范围、禁区、验收、规范与相关 skill 的实际路径、整理前基线、完整差异及验证证据。代码整理附受影响的画像／设计说明、保护目的与相关决定；科研整理附相关路线说明与原始证据入口，覆盖各条路线，含落后方案和中间指标。
- 基线要区分本轮改动与原有未提交工作；“看看最近修改”不构成交接。
- 给只读代理可直接读取的差异或历史快照，必要时用临时文件，不在仓库新增审查报告。子代理不继承主会话历史，也未必能访问记忆工具，交接材料要自包含。
- Pi：使用 `subagent_run`，`agent="consolidation-reviewer"`；OpenCode：用原生 `subagent` 选择同名角色。
- DSH：调用 `consolidation_review`（原生 spawn 工具的命名实例，绑定 `consolidation-reviewer` preset）；Codex：用原生 `spawn_agent`，`agent_type="consolidation-reviewer"`。
- Claude Code：用 Agent（Task）工具，`subagent_type="consolidation-reviewer"`；定义在 `~/.claude/agents/`，由 `skills-sync.sh` 随 base 组部署。实际参数以宿主工具 schema 为准。
- 审查期间冻结相关范围，不并行修改。后台调用按宿主完成通知处理，不轮询等待。
- 核实发现后修复，只对受影响部分补审，不设固定轮数。真实 bug 超出整理授权时单列说明。
- 记忆数据库的检索与更新由主会话通过可用工具执行，子代理不直接操作数据库。StrictDoc 改动按项目要求导出，并检查相关正文。

## 5. 防止“整理”制造新堆积

- 优先更新已有实现、主题摘要、索引与当前交付；整理报告、债务台账、交接文档和新一层目录默认不新增。
- 原位维护，不生成 `v2`、`final-final`、兼容副本和内容相同的多份说明。确需新文件时说明其独立职责。
- 不设压缩率、删行数、文件数配额。可报告可复核的实际前后差异，收益只报实测值。
- 意外发现仅在影响本次正确性或验收时继续处理；其它重要问题给出现有证据和重开条件，留给用户决定。

## 6. 向用户交付

默认短答，中文；技术标识、命令与路径原样保留。沿用现有任务记录。

- **状态**：完成／部分／阻塞；具体改动及当前入口。
- **保持与变化**：关键语义保持依据；若含授权纠错，单列实际行为或结论变化。
- **验证**：实际执行的路径、结果与证据位置；计划和推测不写成已完成。
- **未查与风险**：明确未验证内容、保留对象的原因，以及真正需要用户决定的问题。

只读审查按严重性给具体情境、位置、最小修法和不修的后果。“局部例外与误用”按 Reviewer 合同交代发现或覆盖范围，其余无发现的栏目跳过。

完成的标准：授权范围内的真实冗余、临时囤积和失效入口已经收敛，必要调用与当前交付一致，关键语义与证据没有丢失，未确认部分如实暴露。文本变短只是副产品。
