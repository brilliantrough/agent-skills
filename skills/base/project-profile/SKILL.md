# Project Profile：把项目当前形态讲清楚

**Ponytail 风格：最短但足够完整的项目说明。** 让读者先形成整体认识，再按任务深入相关代码与记忆；基本概念在正文里就能读懂，不需要先打开十几个链接。

## 1. 维护一份入口，不另造知识系统

- 先读项目指令，确认已有画像或等价架构说明；能承担当前整体说明的文档就原位完善，不按名字另建副本。目录树、日志或纯链接清单还需补成完整画像。
- StrictDoc 项目默认使用 `docs/handbook/project-profile.sdoc`；项目已有布局与格式优先，建画像不需要安装依赖、迁移文档或改变版本控制规则。
- 在项目 `AGENTS.md` 或已有接手入口留下实际路径，让 `load-mem` 能找到；那里只放指针。
- 根 AGENTS 的 `user-discipline` 块是用户强制纪律。画像只登记其存在与入口，不复制、不改写；适用纪律由 `discipline` 和各执行阶段直接检查。
- 画像说明当前事实与认识，权威仍在原处：现行意图按有效决策解释，实现按当前源码／配置核实，研究判断按推导、观察和实验等证据限定，运行状态按实测记录。发现冲突时并列说明，由原有权威裁决。
- 只维护授权范围；多个仓库共同构成项目时，讲清各仓归属与跨仓接口，外部库按外部库写。无关目录、私密配置和原始数据不在扫描范围内。

## 2. 先建立整体认识，再写正文

1. **找主线**：从项目目标、README、已有研究说明和有效决策识别问题、交付物、边界及当前阶段；科研主线可以是一个问题，多条求解路线并行，不必先选出唯一赢家。
2. **追真实流程与证据**：工程沿入口 → 调用／数据／状态流转 → 输出核对实现；科研沿问题 → 路线 → 推导／观察／实验核对认识。目录和代码图用于导航，理解要靠读实现；无代码的研究不硬套调用链。
3. **定位设计与方法**：找影响项目的模块边界、接口、约束、研究假设和取舍；理由不明时标未知。历史用来补充理由，现状以当前实现为准。
4. **写一份说明**：用下面的问题检查覆盖，按真实项目取舍章节；简单模块不必单列一节。

| 读者的问题 | 正文要讲清的内容 |
| --- | --- |
| 项目是什么？ | 目标、使用者、交付物、明确不做什么 |
| 当前到哪了？ | 已有能力、当前主线、关键缺口；实现／验证／计划分别陈述，不复制待办清单 |
| 整体怎样运转？ | 主要入口到输出的行为链；关键数据、状态、控制和外部依赖怎样流转 |
| 代码怎样分工？ | 核心职责、边界与依赖，紧邻对应文件和关键符号 |
| 为什么这样设计？ | 设计目的、要防止的具体问题、必须保持的条件、实现位置与取舍；写到具体故障，“为了安全／性能／维护”不够，必要时用短代码说明 |
| 接到需求从哪里改？ | 典型任务 → 首看入口 → 关联改动点／约束；使用真实需求类型 |
| 怎样运行与确认？ | 必要环境前提、启动或验证入口、深入资料位置；标清命令的副作用与未验证项 |

- 正文足以解释整体，链接用来深入。加载 `readable-docs` 成稿；完整目录树、接口清单和聊天历史不贴进画像。
- 重要设计可多写，简单模块一句即可；不设固定字数或压缩率，条件、负结果、边界与未知不因简短而省略。
- 代码只摘解释设计所必需的片段，并标注相对路径与函数／类型名；源码摘录与解释性伪代码明确区分。按路径和符号定位，行号会漂移；实现改变时同步检查摘录。
- 敏感值、临时令牌和个人环境不抄进画像；运行前提指向既有配置入口，当前机器的特例不写成项目通则。

### 重要设计：解释保护什么，不只列出功能

- 用具体场景串起 **要保证什么 → 什么情况下会出问题 → 当前机制与代码位置 → 代价、适用边界或重议条件**。这是解释线索，按需使用；保护分支不逐个新增决策。
- 画像保留理解整体所必需的理由；复杂机制、跨模块约束在已有 handbook／专题说明中按主题展开。短说明与详细记录可以重叠，完整副本只维护一份；知识分工按 `save-mem`，重要理由要能在当前说明里直接找到。
- 依据有效决策、历史证据和相关实现解释设计；推断标为推断，理由未知就留未知。设计意图是否已被实现保证，要看实现验证；前提已变的既定保护，经确认后再删。

### 科研画像：研究地图与实现地图并存

- 先讲研究问题与要获得的认识，再讲主要路线如何贡献；路线可竞争、互补、依赖或分条件适用。理论推导、方法探索、诊断测量都可属于主线，排序不看有没有代码或最近跑得多。
- 每条主要路线简述：核心思路／假设、当前证据及适用边界、推进状态、关键未知与下一步；关联已有推导、代码、配置、结果和说明位置。沿用现有路线名称，不新增路线文件或登记系统。
- **推进状态与认识状态分开**：正在做／暂停／阶段完成，分别可能对应尚属假设／局部支持／证据冲突／条件性否定。沿用项目词汇；实验完成后假设仍可能未成立，暂停的路线仍可能成立。
- 画像保留路线全景与有价值的分歧，包括暂未领先的方法；细节与原始证据留在已有专题和产物里。无证据的想法如实标明。

## 3. 持续维护，不每轮重建

| 时机 | 最小动作 |
| --- | --- |
| 用户首次要求，或 `migrate-mem` 初始化项目记忆 | 从证据建立画像；已有等价文档则补齐，复用已有调查 |
| 新 Agent 接手／`load-mem` | 项目指令之后先读画像，再按任务读相关规范、记忆与专门资料；画像缺失时正常继续，不自动发起全仓调查 |
| `save-mem` 发现项目形态、主要路线或关键认识改变 | 直接改写已有段落与来源，合并同主题更新，删去重复／失效表达；整体未变则不刷新 |
| `consolidator` 阶段整理 | 在授权范围内校准画像与实现、研究证据、决策的对应，删失效描述、突出问题及主要路线；不另造精简版 |

- 形态变化包括目标／阶段、模块职责、主流程、公开接口、关键设计、运行方式或重要能力边界的变化。重构移动入口、合并职责或改变保护机制时，局部更新相关定位与设计解释；仅函数内部精简、整体认识未变时不刷新。使用方式变化另同步原有 README／手册。
- 研究路线加入／暂停／重开、关键假设被推翻或证据强度实质变化，即使代码目录未变也局部更新；普通运行进度和单次指标波动不触发更新。
- 更新前核对受影响实现或研究证据，保留仍有效内容；画像缺失时，普通保存只提示可用本 skill 建立。
- 文件头简记最近核对日期、依据的版本或工作区状态及覆盖边界。局部更新只说明本次核对部分；无 Git 项目按实际来源记录。
- 发现漂移时先核实与当前任务相关的部分，再据权限修正或报告，范围限于受影响段落。画像帮助定位，修改前仍须读取相关真实实现。

## 4. 核对与停止

- **事实核对**：路径／符号确实存在，核心流程有源码依据；摘录仍匹配，链接可达；计划、历史方案和静态检查结果没有被写成当前运行能力。
- **设计核对**：关键保护目的、条件与实现是否对应？说明能否解释看似多余的结构为何仍有必要，或哪些前提已失效？重要理由在当前说明里能找到，未知与未验证仍可辨认。
- **研究核对**：各主要路线的假设、证据、推进状态与结论边界是否仍一一对应？共同问题、路线关系、分歧和关键未知可见；未执行、暂停、证据不足与条件性失败各按实际状态写。
- **接手核对**：仅从画像能否解释主要工作方式与边界？拿真实任务推演，能否指出该看哪些实现或研究材料、为什么、哪些关联约束不能漏？若仍要漫游全仓才能作答，补上缺少的关系。
- **维护核对**：是否只有一个当前入口？历史细节、重复规范和流水是否留在了原处？画像只保留帮助后续判断的内容。
- StrictDoc 按项目现有 grammar 写入，运行 `strictdoc export .` 并检查相关导出正文。导出通过只说明格式正确，事实仍按上面几项核对。
- 达到本次范围就停。短答交付路径、建立／更新范围和实际验证，说明未覆盖部分；不新增画像生成器、扫描服务、报告或管理台账。
