# Verification：项目驱动的功能复核

套件只提供角色和证据纪律：**简洁优先，覆盖关键风险，不追求形式上的大而全。** 具体验收条件、命令、fixture、平台和运行环境由项目决定，通用 skill 不预制测试矩阵。

## 分工

- **主 Agent**：先完成自己的最小真实验证，对实现和证据负责；新功能验证后，把最小可执行条目接入项目现有检查入口。
- **`verification-reviewer`**：标准档或强制复核时独立检查需求覆盖、真实行为和测试有效性；聚焦当前功能，并默认快查相关旧条目；不编辑实现，不作整理签收。
- **`consolidation-reviewer`**：只在显式整理后审查 Codebase／API 语义、真实保护、简洁性及误删／该删未删。
- **lint／schema／类型检查**：执行确定性规则，不证明功能正确；Reviewer 不冒充这些工具的结果。

## 先读项目，再决定怎么验

优先读取项目的 `AGENTS.md`、测试说明、现有检查入口和验收文档。由当前需求与本地资料确定：

1. 用户可见结果和必须保持的行为；
2. 最小真实路径、关键失败路径与高风险场景；
3. 可用 fixture、隔离方式、平台及成本边界；
4. 哪些证据必须由真实宿主或用户实机提供。

项目没有现成矩阵时，按当前需求选择最小覆盖并说明假设，不在套件里另造通用矩阵。已有测试能覆盖时不新增平行验证器；确需新回归，接入项目现有入口。

## 条目随功能累积

新功能通过针对性验证后，主 Agent 必须留下一个**最小可重复条目**：优先在现有测试增加一个场景，并接入原有统一入口，不另建台账或测试框架。条目只保留一个关键行为、真实执行入口、明确预期和必要的前置条件；能一条命令重跑，不为追求全面把单条写成长矩阵。

用户明确排除的文件不能为补测试而修改；必要覆盖无法在授权范围内完成时，报告缺口，确需改动则先请求授权。

风险有可观察的失败条件且能在授权内复现时，把它变成原有入口的一条验证；已覆盖就引用已有条目。未能验证的前提只留阻塞的决定和解除条件。单条验证通过只关闭它实际覆盖的风险。

### 生成：从真实入口派生，不问用户

新功能落地时由 Agent 自己读出该验什么，不让用户逐次口述：

1. 读代码与项目资料，确定用户可见表面（Web UI、CLI/TUI、API、桌面端、库）、启动方式、可编程驱动手段（已有 Playwright／Cypress 规格、PTY／tmux、curl 可用端点）、可捕获的证据（截图、终端记录、响应体、日志、退出码、数据库状态）、能否并行起实例。
2. 优先复用已有 harness 和现有测试位置。只有真实表面无法驱动时才新建最小 helper，并把调用方式写进条目。
3. 条目写进项目已有的登记位置（测试文件、`tests/README` 或项目验证文档），不新建第二份台账。条目只保留一个关键行为、真实执行入口、明确预期、必要前置条件。
4. **交付前实跑一次**：启动 → 就绪判定（可用，不是进程活着）→ 走一遍该行为 → 留下证据 → 清理自己启动的实例。没跑过的是草稿，不是条目。

多个用户可见表面时，用一张极简 map 让维护可扫描：一个 surface 一行，写清入口、驱动手段、证明形态、前置条件。单一表面不建 map，直接在登记位置写条目。

纯内部重构、文档修改和一次性探针不触发这一步；条目不等于自动化测试，文档化的手工驱动路径加证据同样成立，不为此新建测试框架。

### 维护：三分法与终局

条目会随应用变化腐化。需要系统性复查时，按 surface 逐个走一遍，不要逐句校对：

- **源码一遍**：每个 surface 派一个只读角色（或自己顺序走），回答"这个功能今天从源码怎么走通"，标出疑似漂移并附引用，回一条可执行的验证配方。
- **实跑一遍**：即使源码看起来干净也必跑。驱动前先做就绪检查；任何一次驱动失败后重新检查再继续；失败迭代的残留必须清掉，已捕获的证据必须活过清理。
- **三分处理**：行为对但登记与用户视角不符 → 文档漂移，改登记；行为对但 harness 驱动不了 → harness 缺口，修 harness；行为真的坏了 → 产品缺陷，记录给用户，**不得改登记掩盖**。永不为了跑通而削弱条目描述。
- **终局点名**：`clean`（全覆盖、无改动）/ `changed`（一处修正确实已证明）/ `blocked`（说清缺的前置或阻塞）。无法到达的条目只能标 `verified-unreachable`，并写明缺的前置条件（凭据、权限、外部状态）和尝试过的入口；登记里漏写这个前置条件本身就是漂移。

功能删除或语义变化时同步更新或退役条目，不留挂空指针。条目可以随项目增加，单条仍保持简短。

## 复核顺序

Reviewer 每次先复核当前功能，再默认快查与改动相关的旧条目：优先运行短回归，或沿代码检查明显破坏，不要求每次全量重跑。未运行的旧条目如实列出。

## 按档位与风险委派

开发任务默认标准档：主 Agent 完成 `unslop-changes` 与自有验证后调用 `verification-reviewer`。用户显式选择轻量档时，低风险任务（包括小新功能）可不委派，但仍由主 Agent 验证；项目强制复核、跨模块共享接口、数据迁移、权限／防损、发布回滚和证据存疑仍须独立复核。用户明确要求本 Reviewer 时照常调用；用户禁止子代理时报告未完成的独立复核。

轻量不等于低风险。修复不可信文件路径、目录穿越或符号链接越界，即使只改一个文件，也是安全边界：主 Agent 验证后仍须委派 `verification-reviewer`；角色不可用时如实报告未完成。

交接必须自包含：目标与验收条件、基线与完整差异、项目本地验证入口、已有结果与 SKIP、禁区及可用隔离环境。审查期间冻结相关文件。需要联网、真实服务、生产数据或昂贵计算时，必须另有用户授权；Reviewer 不自行扩大范围。

统一规范见 [references/reviewer.md](references/reviewer.md)，宿主只保存原生角色配置：

- Pi：`subagent_run(agent="verification-reviewer")`；OpenCode：同名原生 `subagent`。
- DSH：`verification_review`；Codex：`spawn_agent(agent_type="verification-reviewer")`。
- Claude Code：`subagent_type="verification-reviewer"`。
- Antigravity：不预装固定 Reviewer；T3 `t3-plan-execute` 下由 OpenCode 执行端调用原生 `verification-reviewer`，直接在 Antigravity 会话内修改时披露未注册固定角色（需要时可用原生只读 subagent 按 [references/reviewer.md](references/reviewer.md) 辅助检查，不冒充已注册角色）。

只装 skill 不等于角色已注册，缺失时披露。发现漏装或 live 漂移时，由主 Agent 使用项目现有安装入口显式更新，再复核真实加载；Reviewer 不直接修改 live。临时 `general` 可作功能审查，但不证明该角色已安装或可加载。

## 套件与发布更新

安装器、模板、插件或分发链改动，必须分别记录**源码提交、构建／Release、部署副本、运行进程**；任何一层通过都不能代替下一层验收。

- 从干净检出核对入口资产闭包：直接引用的源码、模板、测试和角色文件必须存在；本机存在但未入库的文件不算交付。
- 按改动覆盖默认取源、敏感配置保留、失败保留旧版、重跑幂等及数据保留。只选与风险相关的场景，不为套件预制全量矩阵。
- 发布后按授权从正式分发源更新，核对部署目标与真实加载；需要重启时明确留给用户。高风险复核必须重跑原始失败夹具或变异，不能只接收新增测试全绿。

## 交付口径

Reviewer 只读仓库，可在独立临时目录运行项目检查和最小复现，不联网、不安装、不读写 live 环境。无法安全隔离就写未验证。这里的只读是行为合同，不是文件系统沙箱；Bash／shell 仍可能写文件，需要硬隔离的项目应使用宿主沙箱或容器。

最终分别报告：已验证行为与证据、发现的问题、SKIP／未验证环境，以及证据来自静态检查、隔离执行、真实宿主还是用户验收。通过只覆盖本次范围，不消除 SKIP，不代替用户最终验收。
