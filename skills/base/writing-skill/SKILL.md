# writing-skill：把经验写成可移植的 skill

遵循 `goal-first`：先指出要纠正的实际行为及其成本，再做最小规则修改。能修现有条款就不新增重叠 skill；公共原则只维护一处，入口保留短指引。技能使用应比临时摸索省事，不能把方法论变成额外的报告、审批和必跑矩阵。

改动前确认维护归属：只修改自维护技能；`grilling`、`diagnosing-bugs` 等第三方上游技能不直接打补丁或覆盖共享副本。保留其方法价值和更新能力；个人差异放自有入口的触发、分工与适用范围。实验矩阵按研究目的判断，探索、消融、Pareto 和论文覆盖不是过度设计。

## 1. 先判定：这内容配不配做 skill

项目结果/经验成库先用`distill-project-kb`找证据、判断价值并让用户补漏确认；已有领域流程完成同等工作时直接复用，不重复筛选。本skill负责skill载体的编写与组织，不替代领域入库规范。知识库可保存带条件的案例事实，不限于纠正行为的指令；skill是使用入口，不是深度上限。

| 判定 | 去处 |
| --- | --- |
| 跨机器/跨项目会重复的**方法／流程**（怎么做、怎么避坑） | skill；其中触发、顺序、必须／禁止、验收与交接写入 `SKILL.md` 主体，不只放 kb／reference |
| 已有上游 skill 完整提供的方法、目录、配方与资源 | 优先作为外部依赖；本地只写触发、分工、适配与个人差异，不先复制再维护 |
| 支持可迁移判断的实测结果、经典数值、配置与反例 | 现有kb-*或独立领域库的条目；带条件、日期与证据，不泛化为保证 |
| 代码、领域契约、工具、案例需共同演化，且已有独立使用与发布需求 | 在独立领域项目维护；主体只保留发现/交接/适配，不因内容“深”或文件多就拆仓 |
| 只服务本项目运转的路径、身份、当前状态 | 记忆系统或host层文档；版本/对象可作为案例条件保留 |
| 一次性流水、尚无迁移价值的见闻 | 不写；昂贵踩坑或有用实测不必等第二次发生 |
| agent本来就会的通识 | 默认略；若真实误用或易混会影响结果，保留具体差异与反例 |

混了本机事实的通用方法 → 写成 skill 时占位符化（`{{路径}}`），本机值进 host 层或记忆；platform-environment-skill-audit 管回流的脱敏底线。

## 2. 定形（写之前想清楚）

- **命名**：kebab-case，动词或名词短语，≤64 字符，目录名=name；前缀可对齐家族（exp-*、accel-*）。
- **放哪**：主体维护的正文放base/research/accel/kb对应组；只此一机放`~/.agents/skills/`。独立领域项目在自己的源仓维护，即使同一作者也不收编副本。
- **如何接外部**：区分套件代装依赖、可选集成和只引用资源。只有明确由setup管理的外部skill才在`skills-external.sh`登记来源/精确名；按需自行安装的领域库只给入口、用途与缺失处理，不自动代装或接管更新。安装副本与来源快照不是第二维护源。
- **分工**：与相邻 skill 的边界一句话写进 description（"装环境用 X，写代码用本 skill"），避免双触发或都不触发。
- **演化性质**：写时定档，明确更新约定。

| 档位 | 适用 | 更新约定 |
| --- | --- | --- |
| 经验演化型 | research 组、kb-*、personal-ui-taste | 写明更新触发、内容、回流方式；知识记日期+证据，研究方法与案例保留适用边界 |
| 事实冻结型 | accel 三件套 | 安装时特化一次；当日回流，之后不动 |
| 固定指令型 | 一次性流程 | 无演化，过期即废弃 |

安装策略：演化型可覆盖刷新；冻结型只装一次。

## 3. description（决定生死的字段）

- 第三人称或祈使，**what + when + 触发词**：做什么、什么时候用、用户会怎么说到它（含中文口语触发词）。
- 只写触发所需，不写实现细节；≤1024 字符。
- 反例："处理文件"（不命中任何话术）；正例："Extract text and tables from PDF files. Use when working with PDF files or when the user mentions PDFs, forms"。

## 4. 正文（高熵、直白、引导强）

- **上限 ~150 行**；只留影响执行的信息；不为凑行数把多个要点挤成一行。
- **先分执行契约与参考知识**：任务匹配且无实时用户指令、用户纪律或安全边界冲突时，流程性 skill 的主体就是本次执行合同。Agent 必须读取 `SKILL.md`，按适用阶段执行，把强制项纳入计划／todo 与完成检查；不得只当普通外部知识随意取舍，也不得只检索片段就声称已遵循。
- **steps 与 reference 分开**：核心步骤内联在 SKILL.md；纯查表、案例和只有部分分支才需要的知识推到同目录附属文件，指针只一层深。主体或当前分支要求读取的 reference 属于执行步骤，必须读取并遵守适用约束，不能因文件位置而降格。
- **衔接动作必须显式**：需要触发另一个 skill、脚本、审查或保存时，写清触发条件、时点、输入／交付和未完成处理，用“调用／执行／交接”；不要写“可参考 X”让关键动作变成可选。
- **每步有完成判据**：这步做完的标志是什么（可观察的输出/状态），没有判据的步骤是废话步骤。
- **自由度按脆弱性给**：易错处给精确命令（照抄可跑），判断处给启发式一句话；不要给菜单让 agent 自己挑。
- **行动规则用强语气**：现阶段模型会把“尽量／适当时／可考虑”等弱词当成可选建议，直接规定默认动作、完成判据和不接受的退路；“保险起见”“以后可能有用”“无法证明绝对安全”“只追加最省事”不能成为不执行的理由。真实保护边界与事实不确定性同样写清：**行动不模糊，边界不含糊，事实不硬说**；强语气不等于无条件删改。
- **细节=差异点**：确切命令、键名、版本行、真实踩过的坑（症状→原因→处置）；删常识、铺垫、重复解释，保留影响判断的条件、原因、例外。
- **leading words**：同一概念在三处重复叙述 → 收敛成一个引导词；每个多余句子都是下次维护的债。
- **关键纪律反复强化**：与任务核心相关、违背代价高的规则，在不同阶段／决策点用同一短句提醒，不算重复；不得为了去重或缩短而删。精简重复内容时，只清理与任务无关的细节和不改变动作的同义复述。
- **时效内容带日期**（版本行、矩阵），未验证的标 `(未验证)`；不写死会过期的结论而不给重查命令。
- **成稿必须走 `readable-docs`**：起草或改写 `SKILL.md`、README、reference 和示例正文前加载它，每次成稿执行短检查；显式润色或模板问题密集的长文必须读取并应用完整目录。按理解需要选择短语、完整句、段落、列表和表格，不把“短语优先／段落作例外”当固定格式。代码、命令、frontmatter、配置、引语与显式 ID 保持原格式和语义，不作文风改写。

## 5. 收尾检查（写完自查）

1. **触发测试**：拿 2–3 句真实用户话术模拟，description 会不会命中？相邻 skill 会不会抢？
2. **执行权威检查（流程性内容）**：核心流程是否都在主体写成必须动作？触发后是否会进入计划／todo、调用必要的衔接操作并在交付前核对？若流程部分仍像一篇“可参考”的知识文档，不得交付；纯知识不按此项强行加步骤。
3. **成稿与双读者检查**：已按 `readable-docs` 完成短检查与必要重写？
   - 对人：目的、条件、动作和例外容易找到，没有套话、模板腔和无效排版。
   - 对 Agent：术语稳定，行为主体与对象明确，触发条件、执行动作、衔接和完成判据没有歧义。
   - 信息密度：还能删哪些字而不丢含义？检查最长条目，拆开独立要点；不按解释与代码的长度比删内容。不把“有人味”写成轶事、情绪或聊天腔，也不把“AI 易懂”写成更多粗体、列表和重复强调。
4. **语气与退路检查**：默认动作是否明确？是否仍有“尽量／适当时”等可绕行弱词？常见借口是否已封住，真实边界和未验证事实是否被误写成绝对结论？
5. **去情境化检查**：grep 本机痕迹（用户名/主机路径/IP），该占位符的占位符。
6. **首次真用**：skill 的价值在第二次被触发时验证；没触发改 description，触发后流程性内容只当参考就修主体指令，不另加一份说明。纯知识核对适用条件、证据与可检索性，不强行加流程。用漏了补触发词，别预先设计用不到的分支（YAGNI）。

## 6. 演化

固定回路：真机改本机副本 → 下载到开发机 → 合入仓库 push → 各机拉新版。

- 落点：最小修改回到 skill 本体，不改结构；规则被推翻时更新对应小节并注明证据。
- 刷新：覆盖刷新组自动；只装一次组显式重装。
- 防丢：本机修改未回流前，别重跑 setup 的覆盖刷新。

| 类别 | 演化协议 |
| --- | --- |
| 知识类（kb-*） | 按其「演化」节记日期+证据 |
| 算力平台类 | accel-skill-template 落盘规则 |
| 品味类 | personal-ui-taste evolution 协议 |
