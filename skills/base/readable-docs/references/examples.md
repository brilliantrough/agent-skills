# 项目技术文本：改写示例

以下均为假设材料，仅示范表达；数字、路径和行为不是对当前项目的实测结论。每组改写只使用原文已有信息。

## 决策：结论与条件分开找

**原文**

> 为了确保升级过程中已有配置能够得到妥善保留，我们决定采用字段级合并的方式。对于本机已经存在的 apiKey 和 baseURL，升级时不会覆盖；非敏感字段则跟随模板更新。此外，本机独有字段不会被删除。如果模板值是占位符，也不会覆盖本机已经填写的值。这一方案的主要目的是避免升级时丢失已有凭据。

**改写**

采用字段级合并，避免升级丢失凭据。

- `apiKey`、`baseURL`：保留本机已有值
- 非敏感字段：跟随模板更新
- 本机独有字段：不删除
- 模板占位符：不覆盖本机已填值

## 对比：单元格写差异，原因放表外

**原文**

PS：避免每台服务器重复安装构建依赖。

## 报告：已验证与未验证不能混写

**原文**

> 本次已经完成插件加载检查，检查过程中没有发现报错，但尚未进行真实上传。因此，目前不能据此判断上传功能已经可用，后续仍然需要在用户环境中完成一次真实上传来确认。

**改写**

- 已验证：插件加载无报错
- 未验证：真实上传；不能认定功能可用
- 待用户确认：在实际环境中完成一次上传

不能压成“插件已验证可用”。那不是精简，而是改了结论。

## 操作手册：动作、条件、预期结果

**原文**

> 当日志出现 E_LOCK 时，需要先暂停写入任务，再运行 tool unlock --dry-run 查看锁占用情况。只有确认没有活跃写入者后，才可以运行 tool unlock。解锁后重新启动写入任务，预期日志不再出现 E_LOCK。如果仍然报错，则停止重试并保留日志。

**改写**

触发条件：日志出现 `E_LOCK`。

1. 暂停写入任务。
2. 运行 `tool unlock --dry-run`，查看锁占用。
3. 确认无活跃写入者后，运行 `tool unlock`。
4. 重启写入任务；预期不再出现 `E_LOCK`。

仍报错：停止重试，保留日志。

“无活跃写入者”是解锁前提，不能省略，也不能藏进 `PS:`。

## 技术说明：因果链不必硬拆

**原文**

> 需要注意的是，由于客户端缓存的有效期为 60 秒，因此当服务端修改配置之后，客户端并不会立即读取新的配置内容，而是会在缓存过期之后的下一次请求中重新读取。这意味着客户端不会在第 60 秒主动刷新配置。

**改写**

客户端缓存有效期：60 秒。服务端改配置后，客户端仍读取缓存；过期后的下一次请求才读取新配置，不会在第 60 秒主动刷新。

保留连续短句：比拆成互相脱离的“缓存 / 过期 / 请求”更清楚。
