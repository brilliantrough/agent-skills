# 信任金字塔：让项目本身承担质量约束

**先让正确做法容易写、错误做法难写，再把稳定规则交给机器检查；文字只承载需要判断的部分。**

这里的“信任”来自环境给出的保证：错误难以写出，写出后被机器拦下，行为有证据可查。每次纠正 Agent 时先问一句：这条纠正能否变成代码结构或确定性检查；确实不能，才写进 `AGENTS.md`。

本 skill 提供工程质量原则与条件化规则配方，关注可维护性、依赖、错误语义和工作区资产；业务目标与研究路线由当前任务决定。加载后仍按当前任务范围工作：启用哪些检查由项目决定，全仓重构、清理和安装工具需要用户授权。

## 五层模型与证据边界

理念来源于 Lauren Tan 的《All Code Is Slop (Except Mine)》。倒金字塔从宽端到窄端排列，越靠宽端约束越硬、杠杆越大，时间优先花在宽端：

| 层 | 要解决的问题 | 项目中的落点 |
| --- | --- | --- |
| Codebase | 错误是否来自 API、模块边界、状态表示或现有示例？ | 在任务范围内改善结构，让正确路径易用、非法状态难构造；清理会被照抄的旧范例，因为 Agent 写代码前会先搜现有调用 |
| Static analysis | 不运行目标程序，能否发现违反明确规则的源码或配置？ | linter、类型检查、依赖检查、schema；除风格外也能发现部分正确性缺陷，报错写明位置、约束和正确替代 |
| Verification | 行为、状态、数值或明确性质是否符合要求？ | Agent 自己运行真实路径并留下验证产物（日志、截图或录像、对照表、timeline）；运行测试、参考对照，必要时做性质测试、模型检查或形式化证明 |
| Prose | 哪些意图、取舍、例外、授权仍需文字表达？ | 保留必要的 AGENTS、skills 和文档；机器已能稳定检查的规则从文字里删掉 |
| Human review | 需求、风险、科学解释和最终取舍是否合理？ | 人裁决机器证据不足以判断的事项；Agent 辅助审查之后仍由人验收 |

原图在静态分析附近还列出 tests/CI。这里按证据性质分层：Static analysis 约束源码与配置，Verification 提供行为或性质证据，二者有交叠（形式化验证可以不运行目标程序）。CI 是执行入口，不单独算一层；分层也不看脚本名或执行者。

**Verification 由 Agent 主动完成，不等人逐次触发。** 验证强度按风险与成本决定。演讲主张把大部分投入放在验证上；本套件的执行 skill 默认从最小真实路径起步，这是面向研究代码迭代成本的取舍，高风险改动相应加强。高成本实验、生产副作用和专项审计按项目授权与预算开展。无报错、退出 0、lint 全绿只说明对应检查通过，预期行为需要另有证据。

## 在日常任务里怎样使用

1. **定位问题与范围。** 读取相关 API、调用方、项目规范和检查入口，指出具体失败模式及影响：易误用的 API、被照抄的旧范例、越界导入，还是缺少行为验证。一般开发只处理当前改动；用户要求建立质量约束时，再查看相关模块。把适用规则和验收带入当前任务记录，不另建计划文件。
2. **选择配方。** 设计或审查质量规则时，读取 [质量规则配方](references/quality-recipes.md) 的相关小节，按实际条件选取，通常只命中六类中的一两类。已有明确规则直接复用，边界未定时与用户讨论。个人偏好和一次局部纠正留在当前任务，不升级成全局禁令。
3. **给出正确路径。** 优先改善结构、接口与示例，并找出仓库里会被照抄的旧用法。禁止某种用法之前，先确认推荐替代能完成合法任务。保留真实输入验证、错误处理和数据保护；不为单一调用者叠加包装层，不按行数强制重构。
4. **落实适合机器的规则。** 判定稳定时读取 [工具选择与检查示例](references/static-checks.md)，接入项目已有入口，并在现有配置或相关说明写清目的、范围、推荐路径、合法例外、检查方式及其边界。重复出现的问题和一次高代价错误都值得固化，不必等复发。存量违规多时按演讲的顺序：先启用规则止住新增，再清理旧用法，最后补强验证；存量少时可以一次迁移完再启用。需要理解意图的判断交给语义审查。
5. **核对并交付。** 运行相关检查，按变更验证实际结果；说明启用的约束、证据和剩余边界。只提出、尚未接线的规则如实标为建议。规则已由代码或检查接管后，删去文档里对应的重复提醒。范围或接口变化时同步规则，过时规则直接修订或删除；豁免指向具体范围和原因。

完成判据：当前问题得到处理，适用约束可执行，证据范围清楚。五层不必都有文件，纯设计请求交付建议即可。质量改善看同类缺陷是否减少、发现时机是否提前、重复审查成本是否下降；规则条数、文件数量、代码行数和模型评分不作为依据。

## 规则配方与已有工作流

| 配方 | 适用信号 | 重点 |
| --- | --- | --- |
| 注释与临时补丁 | 注释反复替 timer、绕路实现辩护 | 修根因，保留真实约束，防止误导范例传播 |
| 依赖与模块边界 | 跨进程导入、核心反向依赖适配层 | 明确依赖方向和通信接口，检查实际依赖图 |
| API 与状态设计 | 隐含调用顺序、互斥参数、非法状态 | 改善契约和状态表示，不追求参数或行数指标 |
| 重复与维护归属 | 同一规则改动总要修改多个副本 | 收拢同一语义，偶然相似的独立逻辑保持分开 |
| 副作用与错误处理 | 任务无人回收、失败被吞掉 | 明确生命周期、取消和失败语义 |
| 工作区与产物管理 | 临时产物混入源码、重复入口和旧报告堆积 | 区分可重建产物与必要证据，明确生成与清理边界 |

- 改代码交给当前 `quick-do`／`steady-do`；本 skill 只提供质量约束。
- 用户请求整理时调用 `consolidator` 并遵守其独立审查要求；普通开发只清理本次自建的临时物。
- 用户请求审查时沿用项目审查入口，按适用配方提出有位置、有后果的发现，只列命中的配方；Agent 的判断标明是判断，不写成确定性工具的结果。
- 研究执行与科学证据交给已安装的 `exp-*`；缺少相关能力时说明并沿用项目流程，不自动安装。

## 静态规则必须可用

- 优先级：已有规则配置 → 已有工具的扩展能力 → 小型项目检查脚本。通用 runner、规则 DSL 和插件注册系统等真有需要时再建。
- 判定来自已确认的规范，同一输入得到同一个可解释的结果。需要猜业务含义、依赖运行数据或模型打分的判断交给审查。
- 错误信息给出位置、违反的约束与正确替代，让 Agent 看到报错就知道怎么修。
- 新规则用最小反例和合法例确认能拦错、不误伤，覆盖该规则涉及的别名、路径和例外。复用已有测试设施或临时输入即可。
- 只扫描适用的项目源码和配置；生成物、vendored 内容及合法适配层按实际规则处理。检查不通过时修代码或修规则，不扩大忽略范围。
- 接到项目已有的 lint/check/CI 入口并让违规返回失败，本地与 CI 用同一配置。只有提示、没有执行入口的规则，交付时标为“尚未自动执行”。
- lint 覆盖的是所声明范围内的违规。功能是否正确靠行为验证，权限、输入边界和数据保护靠运行时机制；lint 拦不住恶意绕过。

## 研究代码的边界

稳定的基础代码适合加依赖方向、API 和配置约束，例如公共 `core/` 不反向依赖 `experiments/*`。实验分支保留探索自由，“某种方法不允许尝试”不写成工程 lint。实际设备行为、数值等价、数据泄漏、指标可信度和科学主张需要运行或研究设计证据，由 `exp-*` 处理。
