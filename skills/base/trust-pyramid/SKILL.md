# 信任金字塔：让项目本身承担质量约束

**先让正确做法容易写、错误做法难以写，再把稳定规则交给机器检查。不要用越来越长的提示词代替这两件事。**

本 skill 提供工程质量原则与条件化规则配方，关注可维护性、依赖、错误语义和工作区资产。业务目标与研究路线由当前任务决定。安装只提供方法，不代表项目已启用任何检查；加载不授权全仓重构、清理或安装工具。

## 五层模型与证据边界

理念来源于 Lauren Tan 的《All Code Is Slop (Except Mine)》。从倒金字塔宽端到窄端：

| 层 | 要解决的问题 | 项目中的落点 |
| --- | --- | --- |
| Codebase | 错误是否来自 API、模块边界、状态表示或现有示例？ | 在任务范围内改善结构，让正确路径易用、非法状态难构造 |
| Static analysis | 不运行目标程序，能否发现违反明确规则的源码或配置？ | linter、类型检查、依赖检查、schema；不仅检查风格，也发现部分正确性缺陷 |
| Verification | 行为、状态、数值或明确性质是否符合要求？ | 运行测试、实际操作、参考对照；必要时做模型检查或形式化证明 |
| Prose | 哪些意图、取舍、例外、授权仍需文字表达？ | 保留必要 AGENTS、skills 和文档；机器已能稳定检查的规则不靠反复提醒维持 |
| Human review | 需求、风险、科学解释和最终取舍是否合理？ | 人判断机器证据不足以裁决的事项；Agent 辅助审查不等于人类验收 |

原图在静态分析附近还列出 tests/CI；技术上，运行测试是动态检查，CI 是执行入口。形式化验证可能不运行目标程序，因此也不能把两层简单分成“不运行／运行”。这里按主要目的区分源码约束与行为／性质证据，二者有交叠；不按脚本名或执行者分层。

**Verification 不要求人逐次触发。** Agent 在开发授权内执行必要的轻量验证，项目也可自动运行既定检查；高成本实验、生产副作用及专项审计按项目授权与预算开展，不借本 skill 扩大范围。无报错、退出 0、lint 全绿都只能说明对应检查结果，不能替代预期行为的证据。

## 在日常任务里怎样使用

1. **定位问题与范围。** 读取相关 API、调用方、项目规范和检查入口，指出具体失败模式及影响。一般开发只处理当前改动；用户要求建立质量约束时，再查看相关模块。把适用规则和验收带入当前任务记录，不另建计划文件。
2. **选择配方。** 设计或审查质量规则时，必须读取 [质量规则配方](references/quality-recipes.md) 的相关小节，按实际条件选取；不默认启用全部六类。已有明确规则直接复用，边界未定时讨论，不把个人偏好或一次局部纠正升级成全局禁令。
3. **给出正确路径。** 优先改善结构、接口与示例；不为单一调用者造层层包装，不按行数强制重构。需要禁止某种用法时，先确认推荐替代能完成合法任务；保留真实输入验证、错误处理和数据保护。
4. **落实适合机器的规则。** 在现有配置或相关说明写清目的、范围、推荐路径、合法例外、检查方式及其边界。判定稳定时读取 [工具选择与检查示例](references/static-checks.md)，接入项目已有入口；一次高代价错误也值得固化，不必等复发。需要理解意图的判断交给语义审查，不伪装成 lint。
5. **核对并交付。** 运行相关检查，按变更验证实际结果；说明启用的约束、证据和剩余边界。只提出规则尚未接线时如实标为建议。范围或接口变化时同步规则，过时规则直接修订或删除，不靠无限豁免维持绿灯。

完成判据是当前问题得到处理、适用约束可执行且证据范围清楚，不是五层都有文件。纯设计请求交付建议即可。质量改善看同类缺陷、发现时机和重复审查成本；不以规则条数、文件数量、代码行数或模型评分代替。

## 规则配方与已有工作流

| 配方 | 适用信号 | 重点 |
| --- | --- | --- |
| 注释与临时补丁 | 注释反复替 timer、绕路实现辩护 | 修根因，保留真实约束，防止误导范例传播 |
| 依赖与模块边界 | 跨进程导入、核心反向依赖适配层 | 明确依赖方向和通信接口，检查实际依赖图 |
| API 与状态设计 | 隐含调用顺序、互斥参数、非法状态 | 改善契约和状态表示，不追求参数或行数指标 |
| 重复与维护归属 | 同一规则改动总要修改多个副本 | 收拢同一语义，不合并偶然相似的独立逻辑 |
| 副作用与错误处理 | 任务无人回收、失败被吞掉 | 明确生命周期、取消和失败语义 |
| 工作区与产物管理 | 临时产物混入源码、重复入口和旧报告堆积 | 区分可重建产物与必要证据，明确生成与清理边界 |

- 改代码交给当前 `quick-do`／`steady-do`；`trust-pyramid` 提供质量约束，不再建执行流程。
- 用户请求整理时调用 `consolidator` 并遵守其独立审查要求；普通开发仅清理本次自建临时物，不自动全仓整理。
- 用户请求审查时沿用项目审查入口，按适用配方提出有位置、有后果的发现；不机械列完六类，也不把 Agent 判断当确定性工具结果。
- 研究执行与科学证据交给已安装的 `exp-*`；缺少相关能力时说明并沿用项目流程，不自动安装。

## 静态规则必须可用

- 优先级：已有规则配置 → 已有工具的扩展能力 → 小型项目检查脚本；不要先写通用 runner、规则 DSL 或插件注册系统。
- 判定来自已确认规范；同一输入应得到可解释的结果。需要猜业务含义、运行数据或模型打分的判断，不包装成确定性 lint。
- 错误信息给出位置、违反的约束与正确替代。检查不只报“不允许”，也应让 Agent 知道怎么修。
- 新规则用最小反例和合法例确认能拦错、不误伤；包括该规则涉及的别名／路径／例外。复用已有测试设施或临时输入即可，不为此新建测试框架。
- 只扫描适用的项目源码／配置；生成物、vendored 内容及合法适配层按实际规则处理。不能为了绿灯扩大忽略范围或放松标准。
- 接到项目已有的 lint/check/CI 入口并让违规返回失败；本地与 CI 用同一配置。只有提示、没有实际执行入口的规则，不能声称已经形成自动约束。
- lint 发现的是所声明范围内的违规，不证明整个功能正确，也不是防恶意绕过的安全边界。真实权限、输入边界和数据保护仍需运行时保证。

## 研究代码的边界

稳定基础代码可以有依赖方向、API 和配置约束；实验分支保留必要探索自由，不把“某种方法不允许尝试”伪装成工程 lint。实际设备、数值等价、数据泄漏、指标可信度和科学主张通常需要运行或研究设计证据，由现有 `exp-*` 处理；静态通过不能证明研究成立。
