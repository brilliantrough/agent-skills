# 信任金字塔：把可重复的判断落实到工程中

**先让正确做法容易写、错误做法难以写，再把稳定规则交给机器检查。不要用越来越长的提示词代替这两件事。**

本 skill 保存开发原则，不是项目初始化器或统一验证框架。与 `goal-first` 配合：在当前任务里选择有效落点，不因加载本 skill 自动全仓重构、安装工具或生成检查脚手架。

## 五层模型与本套件分工

理念来源于 Lauren Tan 的《All Code Is Slop (Except Mine)》。从倒金字塔宽端到窄端：

| 层 | 要解决的问题 | 本套件的用法 |
| --- | --- | --- |
| Codebase | 错误是否来自 API、模块边界、状态表示或现有示例？ | Agent 在用户指导和任务授权内改进结构，让正确路径成为自然用法 |
| Static analysis | 能否不运行目标程序，就发现违反明确规则的代码或配置？ | Agent 复用 linter、类型检查、依赖检查；必要时编写小规则，接到项目原有检查入口 |
| Verification | 实际行为、状态、数值或形式化模型是否符合要求？ | 用户发起专项检查或已有任务约定时执行；沿用项目工具与研究方法 |
| Prose | 哪些意图、取舍、例外、授权仍需文字表达？ | 保留必要 AGENTS、skills 和文档；机器已能稳定检查的规则不靠反复提醒维持 |
| Human review | 需求、风险、科学解释和最终取舍是否合理？ | 由人类主导和触发；可委托 Agent 辅助审查，不能把模型自查冒充人类验收 |

原图在静态分析附近还列出 tests/CI；技术上，运行测试属于动态检查，CI 是执行检查的入口。按检查对象和方法分类，不按脚本名分类。上述人机分工是本套件的使用约定，不把它归因成讲者要求。

**重点建设前两层，不等于取消正常开发验证。** 已约定的 smoke、回归、必要数值检查和项目强制检查照常执行，不等用户逐项重批；不得自行扩展成专项审计、全量实验或形式化验证。后几层也可由 Agent 执行，但触发、范围与验收责任沿用用户和项目约定。

## 在日常任务里怎样使用

1. **定位真实失败模式。** 读取当前 API、调用方、规范和检查入口，指出什么写法会造成什么问题。已有足够清楚的规则直接复用；边界未定时先讨论，不把个人偏好写成硬错误。
2. **先检查 Codebase。** 能否消除重复实现、收拢真实共享边界、改善参数或状态表示、替换误导示例？优先解决错误来源；不为一个调用者新增层层包装，不以本原则授权无关重构。
3. **再决定静态约束。** 规则稳定、判定明确且值得反复执行时，配置现有工具；它表达不了时才考虑插件或小型 AST／结构检查。已知一次高代价错误也可以固化，不必等第二次损失。API 改进与 lint 可配合：前者提供正确路径，后者阻止旧用法回流。
4. **把判断依据放回项目。** 在现有配置、规范或相关说明中写清规则意图、适用范围、合法例外、推荐替代及检查命令；不另建统一规则台账。检查实现和具体 API 留在项目，套件只维护通用方法。
5. **按现有工作流交付。** 运行相关检查和约定的真实路径；指出拦住了什么、仍需运行或人工判断什么。边界改变时同步规则及示例，规则过时则删除，不靠不断追加豁免维持。

完成判据是当前问题得到处理且证据范围清楚，不是五层都有文件或工具。纯讨论只给落点建议，不据此执行项目改造。

## 静态规则必须可用

- 优先级：已有规则配置 → 已有工具的扩展能力 → 小型项目检查脚本；不要先写通用 runner、规则 DSL 或插件注册系统。
- 判定来自已确认规范；同一输入应得到可解释的结果。需要猜业务含义、运行数据或模型打分的判断，不包装成确定性 lint。
- 错误信息给出位置、违反的约束与正确替代。检查不只报“不允许”，也应让 Agent 知道怎么修。
- 新规则用最小反例和合法例确认能拦错、不误伤；包括该规则涉及的别名／路径／例外。复用已有测试设施或临时输入即可，不为此新建测试框架。
- 只扫描适用的项目源码／配置；生成物、vendored 内容及合法适配层按实际规则处理。不能为了绿灯扩大忽略范围或放松标准。
- 接到项目已有的 lint/check/CI 入口并让违规返回失败；本地与 CI 用同一配置。只有提示、没有实际执行入口的规则，不能声称已经形成自动约束。
- lint 发现的是所声明范围内的违规，不证明整个功能正确，也不是防恶意绕过的安全边界。真实权限、输入边界和数据保护仍需运行时保证。

设计具体 lint 或选择工具时，读取 [静态约束的实现选择](references/static-checks.md)。不要仅因加载本 skill 安装表中所有工具。

## 研究代码的边界

稳定基础代码可以有依赖方向、API 和配置约束；实验分支保留必要探索自由，不把“某种方法不允许尝试”伪装成工程 lint。实际设备、数值等价、数据泄漏、指标可信度和科学主张通常需要运行或研究设计证据，由现有 `exp-*` 处理；静态通过不能证明研究成立。
