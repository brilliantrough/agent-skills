# 条件化质量规则配方

这些配方用于选择项目约束，默认都不开启。先核实项目已有契约与实际问题，再确定目录、API 和例外。例子只示意结构，接入前按项目实际改写。

每条落地规则在项目现有位置写清六项：**防止的问题、适用范围、推荐写法、检查方式、合法例外、检查边界**。有确定性判据才自动拦截；意图、取舍和维护价值由语义审查判断。工具映射见 [static-checks.md](static-checks.md)。

## 1. 注释与临时补丁

**防止的问题**：注释把临时绕路解释成合理架构，后续 Agent 照抄；只删注释的话，脆弱实现仍在传播。

**适用条件**：注释在为固定延迟、重复初始化、绕过接口、忽略错误等做法辩护，或只是复述代码。`hack`、`TODO`、`workaround` 字样只是线索，要看实现本身。

**推荐结构**：先修正状态、事件或 API 契约，再删掉复述与自我辩护的注释。保留代码无法表达的外部限制、单位、算法依据、协议契约，以及法定许可说明。确需临时补丁时，限定在最小位置，写明限制及移除条件。

反例：用一句“必要处理”代替时序依据。

```js
// 必须等 100ms，这个技巧能确保视图就绪。
setTimeout(() => view.update(data), 100);
```

改进方向：若项目已有明确的就绪信号，使用真实状态。

```js
await view.ready;
view.update(data);
```

**检查方式**：审查注释是否会诱导复制错误范例，连同实现一起处理。某一层已有可靠替代、并明确禁止任意 timer 时，才为该层配置禁用 API／语法规则，报错里写出替代接口。

**合法例外与边界**：退避、节流、动画调度、协议等待是 timer 的合法用途，按模块边界放行。`view.ready` 的拒绝、取消及释放语义仍须处理并验证；把 timer 包进 `waitReady()` 没有修掉根因。注释质量靠审查判断，关键词和数量给不出完整结论。

## 2. 依赖与模块边界

**防止的问题**：跨运行环境导入实现、核心反向依赖适配层、循环依赖，或从稳定公共代码依赖某个实验的内部实现。

**适用条件**：项目已有不同进程、宿主、稳定性或职责边界。单文件工具不必为套规则先拆出层次。

**推荐结构**：沿职责规定依赖方向；共享契约保持轻量，运行环境的实现留在对应侧。公开入口足够时，不要求每个目录再增加一个 barrel／facade。

Electron 示例，箭头表示允许的代码依赖：

```text
electron-main     -> contracts
electron-renderer -> contracts
contracts        -X-> 任一进程实现
electron-main    <-X-> electron-renderer
```

反例：renderer 从 `electron-main/db` 导入函数。改进：renderer 调用经过明确授权的 preload／IPC 接口，由主进程持有数据库；共享消息类型放入 `contracts`。类型导入虽然在编译后被擦除，默认也不跨边界深导入私有实现，是否允许按项目声明。

研究项目可采用 `experiments/* -> core`，禁止 `core -> experiments/*`；两个实验确需共享时，先确认语义一致，再提取稳定实现。

**检查方式**：使用能解析项目路径别名与模块系统的依赖图工具，检查禁止方向、循环及规则要求的间接依赖。静态导入限制只适合范围明确的直接边；启用前确认重导出、动态导入和解析失败各自怎样报告。

**合法例外与边界**：测试夹具、代码生成和兼容适配可按确切路径或依赖边声明例外，排除范围限于规则确实不适用的代码。进程隔离、IPC 输入校验和权限靠运行时机制保证；依赖图通过之后，通信安全和 UI 是否卡顿仍要实际运行确认。

## 3. API 与状态设计

**防止的问题**：调用方需要记住隐藏顺序、维护无效参数组合、猜资源所有权，或反复复制相同的补救逻辑；配置键拼错后静默回退默认值也属此类。

**适用条件**：当前接口已经导致误用或理解负担，或即将形成多个调用方共享的契约。行数、参数数目、圈复杂度只用作定位信号。

**推荐结构**：用明确的操作和状态表达合法选择；资源获取、失败和释放有清楚的责任方。先沿用语言和项目已有的类型与错误机制，不新建通用结果框架。

反例：`save(path, true, false)` 要靠记忆解释两个开关，还可能表达不支持的组合。若项目恰有“创建新文件”和“替换现有文件”两种行为，可改为：

```ts
type SaveMode = "create" | "replace";
save(path, { mode: "create" });
```

**检查方式**：类型检查约束调用形状；废弃入口可用禁用 API 规则阻止回流，报错写明新签名。审查隐藏前提、兼容调用方和错误语义；对文件已存在、权限失败等实际结果做行为验证。

**合法例外与边界**：真实的独立布尔选项不必改成枚举；协议、性能热点、公开兼容接口可以保留底层形态，不为消灭一项指标扩大抽象。外部输入仍需验证，并发写入和资源回收仍需运行确认，类型检查覆盖不到这两处。

## 4. 重复与维护归属

**防止的问题**：同一语义的多个手写副本逐渐漂移，每次修复都要找到并同步多个实现。

**适用条件**：这些实现应当共同演化，差异仅是宿主适配或表示形式。代码相似只是线索，先确认职责是否相同。

**推荐结构**：共享稳定核心，适配层只处理真实差异。生成物从唯一源重建；确需独立运行或多语言实现时保留边界，用共同契约验证结果。

反例：每个宿主插件各自实现相同的结果解析和落盘策略。改进：共用已有核心函数，各宿主仅负责参数、事件和展示。反过来，两项实验的损失函数只是当前公式碰巧一致，应允许独立探索，不急于合并。

**检查方式**：语义审查确认哪些实现确实同源，重复检测工具只提供线索。已声明唯一入口时，可检查其它入口是否绕过它。确有多实现兼容需求时，对各实现运行同一组契约样例；比较的是行为，不要求源文件字节相等。

**合法例外与边界**：独立发布、多语言边界、vendored 代码和必要的生成副本可以保留多份。自然分工的逻辑保持分开，独立证据和合法实现照常保留。

## 5. 副作用与错误处理

**防止的问题**：任务、监听器、timer、连接没有生命周期归属；失败被吞掉，取消被当成普通错误重试，或返回伪造的成功值。

**适用条件**：代码创建异步工作、访问外部资源，或把底层结果转换成对外状态。

**推荐结构**：创建者或明确的接收者负责释放；失败、取消和可恢复降级三者可区分。重试限定具体错误、次数或时间上限与幂等前提，集中在一层。

反例：

```python
try:
    write_config(path, value)
except Exception:
    pass
return True
```

改进：沿用项目错误契约向上传播；捕获只用于明确恢复、转换错误或补充必要上下文，并保留失败原因。不能恢复时让调用方知道写入失败。

**检查方式**：现有 linter 可检查部分空捕获、盲目捕获、未处理 Promise 和资源用法，例如 Ruff 的 [`E722`](https://docs.astral.sh/ruff/rules/bare-except/)、[`BLE001`](https://docs.astral.sh/ruff/rules/blind-except/)（2026-11-18 核对）；采用前核对语言及类型信息要求。失败传播、取消、重试次数、关闭后回调是否继续执行，需要运行验证，例如做一次故障注入或生命周期循环。

**合法例外与边界**：非关键遥测可以 best effort，用户数据写入的错误必须传出。合法后台任务有监督、错误出口和终止约定，可以不立即 await。timer 的问题在缺少归属与正确时序，有归属的 timer 照常使用。

## 6. 工作区与产物管理

**防止的问题**：一次性调试脚本变成隐式入口，生成物混入源码，旧报告与现行结论并存却没有状态区别。

**适用条件**：任务会生成文件，或项目已有难以判断用途和生命周期的内容。普通开发只处理本次创建的临时物，整体整理遵守授权范围。

**推荐结构**：沿用项目现有的源码、测试、结果和临时位置，生成命令明确输出位置及生命周期。需要保留的实验证据、交付物与可重建缓存分开；正式脚本有真实调用者，没有调用者的删除。

反例：根目录出现 `debug-final2.py`、`report-new-final.md` 和几份没人使用的结果副本。改进：可复用逻辑并回正式入口，结论更新现有报告；必要的原始结果按项目证据约定保留，本次一次性探针在用途结束后移除。

**检查方式**：对已经约定的目录、允许入库的产物类型、引用和生成出口做结构检查。审查用途与维护归属，必要时实际生成并检查输出和清理行为。`.gitignore` 只是版本控制策略，`git status` 干净时目录里仍可能有孤儿脚本。

**合法例外与边界**：用户未提交的工作、私密配置、许可证、原始数据、复现依据和当前交付必须保留；删除前按用途和归属判断，文件名、年龄、扩展名或未跟踪状态不足以作为依据。一次性产物用途已结束且归属明确时直接清理，不新增清理台账或长期保留清单。
