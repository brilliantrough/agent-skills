# 条件化质量规则配方

这些配方用于选择项目约束，不是默认开启的禁令。先核实项目已有契约与实际问题，再确定目录、API 和例外。例子只示意结构，不是可直接部署的框架。

每条落地规则在项目现有位置写清：**防止的问题、适用范围、推荐写法、检查方式、合法例外、检查边界**。有确定性判据才自动拦截；意图、取舍和维护价值由语义审查判断。工具映射见主体指向的 `static-checks.md`。

## 1. 注释与临时补丁

**防止的问题**：注释把临时绕路解释成合理架构，后续 Agent 照抄；删除注释后，脆弱实现却仍在传播。

**适用条件**：注释在为固定延迟、重复初始化、绕过接口、忽略错误等做法辩护，或只是复述代码。不能仅凭 `hack`、`TODO`、`workaround` 字样判错。

**推荐结构**：先修正状态、事件或 API 契约；删掉复述与自我表扬。保留代码无法表达的外部限制、单位、算法依据、协议契约，以及法定许可说明。确需临时补丁时，限定在最小位置，说明限制及移除条件。

反例：用一句“必要处理”代替时序依据。

```js
// 必须等 100ms，这个技巧能确保视图就绪。
setTimeout(() => view.update(data), 100);
```

改进方向：若项目已有明确的就绪信号，使用真实状态。

```js
await view.ready;
view.update(data);
```

**检查方式**：审查注释是否会诱导复制错误范例，连同实现一起处理。只有在某层已有可靠替代、明确禁止任意 timer 时，才配置该层的禁用 API／语法规则。

**合法例外与边界**：退避、节流、动画调度、协议等待可以合法使用 timer；不可一概禁止。`view.ready` 的拒绝、取消及释放语义仍须处理并验证；将 timer 包装成 `waitReady()` 不等于修好根因。注释质量不能靠关键词或数量完整判定。

## 2. 依赖与模块边界

**防止的问题**：跨运行环境导入实现、核心反向依赖适配层、循环依赖，或从稳定公共代码依赖某个实验内部实现。

**适用条件**：项目已有不同进程、宿主、稳定性或职责边界。单文件工具不必为套规则先拆出层次。

**推荐结构**：沿职责规定依赖方向；共享契约保持轻量，运行环境的实现留在对应侧。公开入口足够时，不要求每个目录再增加一个 barrel／facade。

Electron 示例，箭头表示允许的代码依赖：

```text
electron-main     -> contracts
electron-renderer -> contracts
contracts        -X-> 任一进程实现
electron-main    <-X-> electron-renderer
```

反例：renderer 从 `electron-main/db` 导入函数。改进：renderer 调用经过明确授权的 preload／IPC 接口，由主进程持有数据库；共享消息类型放入 `contracts`。**类型导入被擦除也不应成为跨边界深导入的默认借口**，具体规则是否允许需按项目声明。

研究项目可采用 `experiments/* -> core`，禁止 `core -> experiments/*`；两个实验确需共享时，先确认语义一致，再提取稳定实现。

**检查方式**：使用能解析项目路径别名与模块系统的依赖图工具，检查禁止方向、循环及规则要求的间接依赖。静态导入限制只适合范围明确的直接边；必须确认重导出、动态导入和解析失败会怎样报告。

**合法例外与边界**：测试夹具、代码生成和兼容适配可按确切路径／边声明例外，排除范围限于规则确实不适用的代码，不能为绿灯扩大忽略。进程隔离、IPC 输入校验和权限仍靠运行时机制；依赖图通过不能证明通信安全或没有 UI 卡顿。

## 3. API 与状态设计

**防止的问题**：调用方需要记住隐藏顺序、维护无效参数组合、猜资源所有权，或反复复制相同的补救逻辑。

**适用条件**：当前接口已经导致误用或理解负担，或即将形成多个调用方共享的契约。行数、参数数目、圈复杂度只能作为定位信号。

**推荐结构**：用明确的操作和状态表达合法选择；资源获取、失败和释放有清楚的责任方。先沿用语言／项目已有的类型和错误机制，不创建新的通用结果框架。

反例：`save(path, true, false)` 要靠记忆解释两个开关，还可能表达不支持的组合。若项目恰有“创建新文件”和“替换现有文件”两种行为，可改为：

```ts
type SaveMode = "create" | "replace";
save(path, { mode: "create" });
```

**检查方式**：类型检查约束调用形状；废弃入口可用禁用 API 规则阻止回流。审查隐藏前提、兼容调用方和错误语义；对文件已存在、权限失败等实际结果做行为验证。

**合法例外与边界**：真实的独立布尔选项不必改成枚举；协议、性能热点、公开兼容接口可以保留底层形态。不要为消灭一项指标扩大抽象。类型不能替代外部输入验证，也不证明并发写入或资源回收正确。

## 4. 重复与维护归属

**防止的问题**：同一语义的多个手写副本逐渐漂移，每次修复都要找到并同步多个实现。

**适用条件**：这些实现应当共同演化，差异仅是宿主适配或表示形式。相似代码不自动意味着同一职责。

**推荐结构**：共享稳定核心，适配层只处理真实差异。生成物从唯一源重建；确需独立运行或多语言实现时保留边界，用共同契约验证结果。

反例：每个宿主插件各自实现相同的结果解析和落盘策略。改进：共用已有核心函数，各宿主仅负责参数、事件和展示。反之，两项实验的损失函数只是当前公式碰巧一致，应允许独立探索，不急于合并。

**检查方式**：语义审查确认哪些实现确实同源；重复检测工具只提供线索。已声明唯一入口时，可检查其它入口是否绕过它。确有多实现兼容需求时，运行同一组契约样例，而非要求源文件字节相等。

**合法例外与边界**：独立发布、多语言边界、vendored 代码和必要生成副本可能合理。不要用一个带大量模式开关的万能函数替代自然分工；不要仅为“减少文件”删掉独立证据或合法实现。

## 5. 副作用与错误处理

**防止的问题**：任务、监听器、timer、连接没有生命周期归属；失败被吞掉，取消被当成普通错误重试，或返回伪造的成功值。

**适用条件**：代码创建异步工作、访问外部资源，或把底层结果转换成对外状态。

**推荐结构**：创建者或明确接收者负责释放；失败、取消和可恢复降级可区分。重试有具体适用错误、次数／时间边界与幂等前提，不在每层重复重试。

反例：

```python
try:
    write_config(path, value)
except Exception:
    pass
return True
```

改进：沿用项目错误契约向上传播；捕获用于明确恢复、转换错误或补充必要上下文，保留失败原因。不能恢复时，让调用方知道写入失败，而不是返回成功。

**检查方式**：现有 linter 可检查部分空捕获、未处理 Promise 和资源用法；采用规则前核对语言及类型信息要求。失败传播、取消、重试次数、关闭后回调是否继续执行，需要运行验证。

**合法例外与边界**：非关键遥测可以 best effort，但不能吞掉用户数据写入错误。合法后台任务有监督、错误出口和终止约定；并非每个 Promise 都必须立即 await。timer 本身不是缺陷，缺少归属与正确时序才是问题。

## 6. 工作区与产物管理

**防止的问题**：一次性调试脚本变成隐式入口，生成物混入源码，旧报告与现行结论并存却没有状态区别。

**适用条件**：任务会生成文件，或项目已有难以判断用途和生命周期的内容；普通开发只处理本次创建的临时物，整体整理遵守授权范围。

**推荐结构**：沿用项目现有源码、测试、结果和临时位置，生成命令明确输出位置及生命周期。需要保留的实验证据、交付物与可重建缓存分开；正式脚本有真实调用者，不因“以后可能有用”保留。

反例：根目录出现 `debug-final2.py`、`report-new-final.md` 和几份没人使用的结果副本。改进：可复用逻辑并回正式入口，结论更新现有报告；必要原始结果按项目证据约定保留，本次一次性探针在用途结束后移除。

**检查方式**：对已经约定的目录、允许入库的产物类型、引用和生成出口做结构检查。审查用途与维护归属；必要时实际生成并检查输出、清理行为。`.gitignore` 只是版本控制策略，`git status` 干净不代表工作区没有垃圾。

**合法例外与边界**：不按文件名、年龄、扩展名或未跟踪状态自动删除；不得把用户未提交工作、私密配置、许可证、原始数据、复现依据或当前交付当临时物。一次性产物的用途已结束且归属明确时直接清理，不新增清理台账或长期保留清单。
