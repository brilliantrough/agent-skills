# 演化协议与反馈记录

本 skill 是活的个人偏好库。用户已授权持续维护：在实际前端合作中，遇到明确的审美反馈与认可，应更新本目录，而不是仅记在某个项目会话里。

## 更新规则

1. **先读再改**：读取实际加载路径下的最新 `SKILL.md`、本文件和相关模式，保留其他场景新增内容；不要根据旧版本覆盖整份文件。
2. **区分证据**：
   - 用户明确说喜欢/不喜欢/以后都如此：记为 **Confirmed**。明确拒绝本身就是证据，不必等待替代品被接受。
   - 用户认可已展示方案：认可该范围的设计，不推断其他颜色模式/设备/业务也被认可。
   - 只有 agent 自己觉得好、截图好看、编译通过或用户未反馈：至多 **Candidate**，不能进入默认规则。
   - 特定品牌/当前项目例外：记为 **Scoped**，不推翻全局偏好。
3. **提炼而非转录**：记录“偏好 + 场景 + 为什么 + 接受/拒绝证据 + 解决方式”，不要复制聊天日志或积累任意 CSS 值。
4. **决定放哪里**：跨场景稳定品味 → `SKILL.md`；已有场景的组件模式 → `patterns.md`；新的独立场景 → 按需建立 `scenarios/<scene-name>.md` 并更新场景索引；时间/证据/状态/变更 → 本文件。相同事实只维护一处正文，其他地方引用 ID。
5. **处理冲突**：最新明确反馈在其适用范围内优先。局部例外保持局部；无法判断是否改全局时，继续当前任务并只问一个针对性问题，不阻塞不相关工作。
6. **允许增删改查**：按下表操作，保持主文件只呈现有效偏好。更新是维护知识，不是无限追加日志；过时、重复和被明确否定的条目可删改。
7. **修订版本**：一批确认的行为/品味更新递增 minor，文字澄清递增 patch；大范围推翻体系再升 major；同步 frontmatter 的 `updated`。不要为每句措辞都建版本。
8. **校验并告知**：检查 frontmatter、相对链接、规则不冲突、引用文件存在。简短告知“已把 X 记入全局品味”，不要声称未写入的文件已更新。
9. **路径不可写时**：给出精确的待应用更新和目标位置，说明尚未持久化；不要悄悄只写项目副本却称为全局更新。

## 按场景增删改查

| 操作 | 做法 |
| --- | --- |
| 查询 | 先按场景索引定位，再查规则 ID、组件、关键词与适用范围；回答当前规则，必要时再查看反馈记录 |
| 新增 | 已有场景补充细节，新增相应规则；新场景经过调试确认后添加场景 ID 和索引。不要整份复制旧场景，也不要提前造空文件 |
| 修改 | 定位原规则就地改写，保留适用的其余内容；同一规则保持稳定 ID，新范围分支单独标注 |
| 删除 | 用户要求删除、规则重复或已失效时，从有效规则和对应索引/引用中清除；删除场景文件前检查引用。记录一句删除原因即可，不强制保存被要求移除的原文 |
| 合并/拆分 | 重复规则合并并更新引用；一个场景出现不同主题/设备下的稳定差异时拆分范围，不互相覆盖 |

规则 ID 使用 T01…，场景 ID 使用 S01…；已有 ID 不复用给无关内容。新增场景先继承仍适用的通用偏好，再记录自己的差异。每轮更新只改本次反馈覆盖的范围。

## 内容与迁移

- 只保存 UI 设计经验。案例、反馈与示例使用通用组件名称，不保留项目叙事、专有名词或功能实现背景；这条要求同样适用于变更记录。
- 新截图使用通用演示内容并随目录保存，用相对路径引用；不依赖临时文件。
- 全部规则是可读 Markdown。其他服务器复制**整个目录**；此机制不会自动联网同步。
- 两台机器都更新了：逐项按稳定 ID、反馈日期和范围合并，保留双方记录；版本号大不等于审美证据新，不盲目覆盖。
- 外部笔记可以指向此 skill，但当前规则应以本目录为准。新场景成熟后再补模式，不提前造空模板目录。

## 反馈记录模板

```markdown
### YYYY-MM-DD · 简短主题 · vX.Y.Z
- 状态：Confirmed / Candidate / Scoped / Superseded / Removed
- 场景与操作：Sxx；新增 / 查询结果 / 修改 / 删除 / 合并 / 拆分（仅实际变更需留记录）
- 范围：页面或组件、设备/主题等
- 证据：用户原话短摘或明确标注的转述；方案有无实际展示/认可
- 规则：Txx；若替代旧项，列出继任规则；删除时记录原因，不重复被移除内容
- 变化与原因：旧行为 → 新行为；解决哪个体验问题
- 参考：相关模式或场景文件，或随 skill 携带的通用演示素材
```
