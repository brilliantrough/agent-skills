# Verification Setup：先剖析问题，先建验证与评价体系

用于开启重要工程开发或科研课题之前（也适用于给已有项目系统补课）：先剖析任务本身与代码／实验现场，与用户对齐并搭好统一的 **验证与评价体系（Verification / Evaluation）** 与静态快拦截，再由这把校准过的尺子反推科学规划，指导后续 Agent 迭代推进。

在面向 Agent 的工作流里，Verification（确定性正反例）与 Evaluation（定量指标、对比基线与质量判据）属于**同一层级的反馈体系**，按任务性质并用。日常单次改动的增量回归与独立复核归 [`verification`](../verification/SKILL.md)；单项规则配方查 [`trust-pyramid`](../trust-pyramid/SKILL.md)。**完整流程只是默认标准档，不是所有任务的必经门槛**；小任务随时走轻量做法或直接跳过，避免无谓仪式感。

## 先判轻重：什么时候跳过或走轻量版

- **直接跳过**：行为与验收命令已经明确的局部小改、一次性探索脚本，不启本技能，直接进 [`quick-do`](../quick-do/SKILL.md) 或 [`steady-do`](../steady-do/SKILL.md) 做完实跑即可。
- **轻量版（简易做法）**：在不涉及高风险边界（数据防损、安全／路径权限、共享接口、项目强制复核或发布）的前提下，用户说“轻量档／简单来／先简单搭一下”，或面对小型工具、独立小实验时，**跳过下方 5 步重流程、不写长蓝图、不做多轮访谈**——直接一步到位定清 **1 条真实入口命令 + 1 个关键正例 + 1 个最怕出错的反例（或 1 个基线指标）**，确认能抓错后立刻推进主任务；仅当用户显式选轻量档时才一并免去单独 Unslop 与独立 Reviewer，触及安全或高风险边界仍须独立复核。
- **标准档（默认）**：跨模块工程、长期项目、高代价失败面或需要严谨对照的科研课题，按下方 1–5 步完整剖析、默认停顿确认并校准尺子。

## 1. 剖析任务与现场（先做功课，拒绝直接动手）

- **先剖析任务本身**：借 [`problem-framing`](../problem-framing/SKILL.md) 拆清本次工程任务或科研课题的真实目标、关键假设、竞争解释，以及最容易自欺欺人的假象（“看似跑通、指标好看或退出 0，但问题并未真解决”的反例），先回答“看到什么证据才算真正做对／做好”。
- **再只读扫描现场**：读取项目根 `AGENTS.md`（含 `user-discipline`）、README、依赖清单、已有检查／测试／评测脚本与 CI 配置；盘点全部用户可见表面或实验产出表面（CLI／TUI、Web／桌面、HTTP／RPC API、库与脚本、插件／多宿主配置、PyTorch／模型或 Agent 管线），列出入口、启动方式与隔离条件。
- 按命中的项目形态读取 [领域风险探针与反伪绿灯清单](references/domain-probes.md) 对应小节，结合真实调用链初筛高代价失败面、定量／质量评价缺口与当前缺失的隔离能力。
- **完成判据**：输出一张简洁的《任务剖析与验证现状快照》（核心目标与必拦反例、现有防线、验证与评价缺口）。

## 2. 对齐验证与评价蓝图（默认停顿点）

- 基于剖析结果提出一份面向本次任务／项目的**验证与评价蓝图草案**，每项写清四件事：防什么具体失误或衡量什么核心质量、采用静态快拦截还是验证／评价判据、运行成本与隔离边界、优先级（P0 推进主任务前必建／P1 后续补充）。
- 只向用户提 2–4 个会改变评价体系的未决问题，每项附推荐答案与简短取舍：
  1. **成败标准与底线事故**：哪些是绝对底线（防丢数据、安全边界、核心契约、数值等价、防数据泄露），哪些本轮暂缓；
  2. **确定性验证与定量／质量评价的组合**：哪些靠正反例二值判定（Verification 形态），哪些靠连续指标、基线对照或分项质量判据（Evaluation 形态）；
  3. **快反馈 vs 真实环境边界**：哪些必须离线隔离、Agent 改完可秒级自跑，哪些依赖真实宿主、GPU、外部服务或人工实机验收；
  4. **推进节奏**：先落地并校准最小可用评价体系，还是确认后立即衔接主任务规划与执行。
- **默认停顿门禁**：未获用户明确确认前，停在蓝图草案并以“验证蓝图待确认，尚未修改项目”收尾，严禁提前改项目文件或跳过评价体系直接推进主任务。在 T3 Code 的 Antigravity 主会话中，蓝图获批且落地跨模块时，可按 [`t3-plan-execute`](../t3-plan-execute/SKILL.md) 委派 OpenCode (GPT) 实施并由原生 Gemini 子代理审阅测试结构与信噪比。

## 3. 设计统一反馈体系（同层协同，Ponytail 护栏）

不另造重型框架或平行平台，只建能持续指导后续迭代的最小可执行反馈，由两类协同信号组成：

- **结构与静态快拦截（毫秒～秒级，零运行）**：把稳定边界、类型、依赖方向、配置 schema、敏感值与入口资产闭包前置为即时报错。工具映射复用 [`trust-pyramid/references/static-checks.md`](../trust-pyramid/references/static-checks.md)；给 Agent 看的报错必须包含位置、违背约束与正确替代。
- **验证与评价体系（Verification / Evaluation，同一层级）**：将两种测量形态收口到项目统一的检查／评测入口与证据口径，按任务性质并用：
  - **确定性正反例（Verification 形态）**：复用项目已有单一入口（如 `scripts/check.sh`、`npm test`、`pytest`），区分快检与慢检；为关键表面提供最小可编程驱动与独立沙箱（临时 `HOME`／数据库／本地 stub，零污染 live），每条核心契约至少覆盖 1 个真实正例与 1 个高代价失败反例；
  - **定量指标与质量标尺（Evaluation 形态）**：当任务涉及模型／算法精度、量化误差、性能与显存、Agent 行为、检索召回或 UI／内容观感时，同样作为一线验收锚点落位——明确代表性样例集（Golden + 边界／难例，区分调优集与留出验收集）、可复现采集脚本、确定性优先＋分项 rubric 的评分口径，以及对比基线与退化门槛。

## 4. 先落“尺子”并校准（红灯与基线证明）

获得用户实施授权后，先最小完整落地这套验证与评价体系，并先校准尺子本身：

- **单一入口与诚实 SKIP**：所有新增静态检查、行为回归与轻量评测接入项目已有统一入口（重型评测单设显式子命令，不阻塞快循环）；缺外部前置（真机宿主、GPU、凭据、外部服务）时必须显式输出 `SKIP` 与原因，并逐条核对 [反伪绿灯清单](references/domain-probes.md#反伪绿灯自检清单)。
- **红灯证明与基线校准**：确定性规则与回归必须在最小违规样例或临时故障注入上**实跑确认会 `FAIL`**、恢复后 `PASS`（红灯证明）；定量或质量评测必须先在当前基线上跑出一份**可复现基线记录**，写清模型／代码版本、seed、数据 split 与环境口径。未校准的尺子不得用来指导后续开发或实验。
- **单一证据说明**：在项目已有验证说明（如 `tests/README.md`；无则就近补在项目约定文档中）记录极简 Surface Map、评价口径与“离线覆盖 vs 真实环境／人工验收边界”，不另建平行台账。
- **遵循项目质量档**：标准档落地后执行 [`unslop-changes`](../unslop-changes/SKILL.md) 清理本次改动，再跑通统一入口并按 [`verification`](../verification/SKILL.md) 完成独立复核。

## 5. 以评价体系反推规划，驱动主任务推进

尺子校准完成后，立刻用它指导后续主任务与长期演化：

- **反推科学规划**：把已落地的正反例、指标基线与红线直接作为 [`plan-brief`](../plan-brief/SKILL.md)（工程）或 `exp-campaign`（科研）的阶段目标与停止条件，据此拆解每一步实现与实验顺序。
- **驱动日常迭代与演化**：主任务按 `steady-do`、`t3-plan-execute` 或 `exp-batch` 边推进边跑这套反馈回路；后续每次新功能由 [`verification`](../verification/SKILL.md) 沿现有入口增量沉淀最小条目并由 `verification-reviewer` 快查旧条目；同类缺陷出现两次由 [`trust-pyramid`](../trust-pyramid/SKILL.md) 升格到静态拦截；条目漂移按 `verification` 的「维护：三分法与终局」翻新。
